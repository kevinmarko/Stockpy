## Branch Workflow

Antigravity IDE has resumed working on this repo alongside Claude Code (as of 2026-07-20). There is
**no fixed multi-agent domain split or per-agent branch-prefix convention** this time — the operator
assigns work to each agent per-task, ad hoc, rather than via a structural file-domain split. Do not
defer to, flag PRs for, or avoid editing any file on the assumption another agent owns it; any file
may be worked on by whichever agent is assigned the task at hand. Branch naming (lowercase-kebab, e.g.
`fix-hmm-lookahead`) is unchanged and applies the same way regardless of which agent opens the branch.

### Start-of-session checklist
1. `git fetch origin && git rebase origin/main` — sync from main before starting.
2. **Low-risk changes** — docs, `.claude/` config (settings, hooks, skills, agents), comments,
   test-only additions, and other non-behavioral edits — may be committed directly to `main`
   after a self-review pass (re-read the full diff, confirm it does what it's supposed to and
   touches nothing else). No branch or PR required for these.
3. **Everything else** — anything touching engines, signals, execution, sizing, validation,
   orchestrators, or other runtime/trading logic — always goes through
   `git checkout -b <short-description>` (lowercase-kebab, e.g. `fix-hmm-lookahead`) and a PR.
   Never commit these directly to `main`.
4. Open a PR when a feature-branch change is complete; do not squash or amend published commits.
5. **After merging any PR**, sync the local main checkout so the next session (in this or any
   other worktree) starts from the merged state instead of a stale `main`:
   `git -C <main-checkout-path> fetch origin && git -C <main-checkout-path> merge --ff-only origin/main`.
   Do this immediately after the merge, not at the start of some future session.

 ## Conventions enforced in this codebase
 
 - **In-app help content (`gui/help_content.py`)**: All operator-facing explainer prose MUST live in `gui/help_content.py` — never hard-code tooltip/expander text directly in `gui/panels.py`. The single-source-of-truth is `GLOSSARY` (terms), `TAB_HELP` (10 tab descriptions), `SECTION_HELP` (section-level tooltips), and `METRIC_HELP` (KPI tooltips keyed by `"<tab>.<metric>"`).
 - **Help-key convention**: Metric tooltip keys follow the form `"<tab>.<metric_name>"` — looked up by `gui.help_content.metric_help(key)`. A missing key returns `""` and renders no tooltip; it **never raises** (CONSTRAINT #6). Never add a default-fallback value in `metric_help` — empty string is the correct sentinel.
 - **Anchor-contract invariant**: Every `GlossaryEntry.guide_anchor` and `TabHelp.guide_anchor` field **must** resolve to a real heading slug in `docs/HOW_TO_GUIDE.md`. Enforced by `tests/test_help_content.py::TestAnchorValidity` (CI) and `Gravity AI Review Suite.py`'s `step_77_help_explainers_audit` check 3. When renaming a heading in HOW_TO_GUIDE.md, grep `gui/help_content.py` for the old slug and update it.
 - **Thresholds in help text**: Values cited in help strings (VIX thresholds, Kelly caps, score gates, …) MUST be read from `settings`, `validation.thresholds`, or `engine.advisory.CONFIG` at module import time — never re-typed as literals in `help_content.py`. This ensures help text stays in sync with the live config without a separate update step.
 - **In-app help content, webapp (`webapp/src/help/helpContent.ts`)**: the Pilots PWA's own curated TypeScript port of the above pattern, scoped to its screens — NOT auto-generated from `gui/help_content.py`, kept independently. `TAB_HELP` (one entry per screen — as of PR #366, all 19 screens have one, keyed by a stable per-screen slug documented in each screen's `<TabGuide tabKey="...">` call) + `GLOSSARY` (term → static string, or `(t: Thresholds | null) => string` for any value sourced from live `GET /thresholds` — never a hard-coded literal for a tunable value; a fixed algorithm constant that isn't part of the `Thresholds` API shape, e.g. the pairs z-score/half-life bands or the macro kill-switch's Sahm/VIX/HY-OAS levels, is fine to state literally IF commented explaining why it isn't threshold-sourced, mirroring the file's own `iv rank`/`vrp` precedent). Rendered by `<TabGuide tabKey=… />` (`webapp/src/components/TabGuide.tsx`) as a dismissible "How this works" panel, expanded on a screen's first visit only. **No anchor-contract field** — `TabHelp`/glossary entries here have no `guide_anchor` equivalent and are NOT checked against `docs/HOW_TO_GUIDE.md`; don't assume the Python GUI's anchor-validity test/Gravity check applies to this file, it doesn't. `helpContent.test.ts`'s `TAB_HELP content integrity` test does enforce that every `keyConcepts` entry resolves to a real `GLOSSARY` key.
 - All data crossing into calculation code goes through the DTOs in `dto_models.py`, not raw dicts/lists.
 - Data fetching always goes through `IDataProvider` implementations in `data_engine.py`.
 - Technical/fundamental math is vectorized — no per-row Python loops.
 - Loops over tickers (in `data_engine.py`, orchestrators) wrap each ticker in try/except so one bad symbol doesn't abort the whole run.
 - New/changed indicators need a corresponding test in `tests/`; numeric drift on existing indicators must stay below 1e-5.
 - Every indicator and forecaster must be verified to have zero lookahead bias using the perturbation tests in `tests/`.
 - Options premium selling (e.g. Put Credit Spreads, Iron Condors) is gated by VRP regime rules: must have `true_ivr > 50`, `VRP > 0.02`, `VIX < 30`, and no `CREDIT EVENT`. If gated, recommender returns `Cash/Wait`.
 - Pairs trading signals are driven by Engle-Granger cointegration test, half-life of mean reversion (between 5 and 60 days), Kalman filter dynamic hedge ratio, rolling spread z-score (entry at |Z| > 2.0, exit at 0 cross or cointegration break rolling ADF p > 0.10, stop loss at |Z| > 4.0).
 - Every backtest execution (e.g. in `simulation_engine.py`) must display the survivorship bias warning and report.
 - Backtests must use the custom `TieredCostModel` for transaction commissions and slippage calculations instead of static assumptions.
 - Gate deployable status of trading strategies on PBO < 0.5 AND DSR > 0.95 in verification audits.

- Deployability gate for strategy harness strictly enforces PBO < 0.5, DSR > 0.95, net net-of-cost Sharpe > 0.5, and Max Drawdown < 30%.
- **Documenting a deployability-gate fix or honest FAIL**: when a `STRATEGY_REGISTRY` adapter is changed to move a strategy toward (or honestly away from) `deployable=True`, add a **Backtest Validation** section (before/after PBO/DSR/Sharpe/MaxDD, the causal lever used, and — for a strategy that stays `deployable=False` — the measured, evidence-backed reason) to the corresponding `docs/signals/<name>.md` (where a live signal module exists) and append an entry to `docs/VALIDATION_STRATEGY_FIX_LOG.md`. See that log's 2026-07 entry for the full worked example (12 strategies, `garch_vol_target`/`multifactor_lowvol_size`/`cross_sectional_momentum`/etc.) and the reusable fix levers it documents (Faber SMA-200 trend gate, empirically-measured turnover correction, variant-count reduction backed by measurement).
- **Options-selling strategies carry an additional tail-scenario stress gate** (`validation/stress_scenarios.py`): they are deployable only if max drawdown is < 50% AND the account survives (no blow-up) in EVERY dated shock window (OCT_2008, FEB_2018, MAR_2020, AUG_2024). Construct the harness with `is_options_selling=True` and a `stress_returns_fn(start, end) -> daily returns`; the gate fails closed if an options-selling strategy is never stress-tested. The stress summary is printed at the top of every options-selling validation report.
- Strategy validation harness cost modeling scales linearly with average daily turnover.
- Quantitative scoring in `StrategyEngine.evaluate_security` must be decoupled into pluggable signal modules under the `signals/` package, using the weighted-sum aggregator. Weights are defined in settings.SIGNAL_WEIGHTS.
- Cross-sectional signals (e.g. `CrossSectionalMomentumSignal`) use the **two-phase hook pattern**: `pre_compute(universe_df, context)` runs once per cycle on the full dashboard DataFrame before the per-ticker loop (called via `global_registry.run_pre_compute()`); `compute(row, context)` reads pre-computed ranks from `context.xsec_percentile_ranks`. All existing per-ticker signals inherit the no-op `pre_compute` and are unaffected.
- The 12-1m cross-sectional return is computed by `compute_xsec_momentum_ranks()` in `main_orchestrator.py` using vectorized `iloc` indexing with `skip_days=22` (1 month skip) and `lookback_days=252` (12 months) — no iterrows, no current-month leakage.
- `config.COLUMN_SCHEMA` now includes `XSec_12_1M` (percent) and `XSec_Momentum_Rank` (percent). These must be present in any Pandera-validated DataFrame.
- New trading rules must be optimized in `vectorbt` and validated in `backtrader` before being added to `strategy_engine.py`.
- Option overlay trend filter in StrategyEngine uses a lookahead-free strong uptrend filter (ROC_12M > 0 and price > SMA_200) falling back to legacy trend strength when not provided.
- `SignalModule.is_active_in_regime(macro: MacroEconomicDTO) -> bool` (default `True`) lets a module opt out of contributing to the aggregate score entirely for a cycle. `SignalAggregator.aggregate()` checks this before adding a module's weighted contribution/explanation — `compute()` still runs (its raw output remains in the returned `outputs` dict for introspection), but a `False` module adds nothing to `final_score`/`score_log`. Use this for regime-fragile signals (e.g. `rsi2_mean_reversion`) rather than relying on `compute()` to self-zero, so the suppression is enforced centrally and is impossible to forget per-module.
- **Operator module disable (`settings.DISABLED_SIGNAL_MODULES`)**: a `list[str]` of signal-module names (JSON array in `.env`, default `[]`) that `SignalAggregator.aggregate()` skips — checked right alongside the `is_active_in_regime` gate, so a disabled module adds nothing to `final_score`/`score_log` and does not affect `meta_label_composite`, while its raw `compute()` output still appears in the returned `outputs` dict for introspection. Empty list reproduces the legacy behavior exactly; honored by BOTH orchestrators. The GUI Command Center's Strategy Matrix tab writes this (and `SIGNAL_WEIGHTS`) via `gui/env_io.py`. New env var: `DISABLED_SIGNAL_MODULES`.
- **Macro Regime Gate (`settings.MACRO_REGIME_GATE_ENABLED`, default `True`)**: operator-controlled bypass for `PreTradeRiskGate.macro_kill_switch_check`. When `True` (autonomous mode), the check vetoes new BUY orders whenever `MacroEconomicDTO.killSwitch` is `True` (Sahm Rule ≥ 0.5, VIX > 30, or HY OAS > 6%). When `False` (hybrid mode), the check returns pass immediately without reading `context.macro` — technical signals run without macro override, useful when idiosyncratic volatility produces a false-positive systemic alarm. The GUI Observability tab (Mission Control) provides a toggle button that writes `MACRO_REGIME_GATE_ENABLED` via `gui/env_io.py` and shows a persistent red warning banner when the gate is off. `scripts/preflight_check.py`'s `check_macro_regime_gate_enabled` is a **blocking** failure when gate is off AND `ALPACA_PAPER=False`; warning-only in paper mode. The state snapshot (`output/state_snapshot.json`) surfaces `sahm_rule`, `high_yield_oas`, and `macro_regime_gate_enabled` so the GUI can display recession telemetry without a live FRED call. New env var: `MACRO_REGIME_GATE_ENABLED`.
- **Persistent orchestrator daemon (`settings.ORCHESTRATOR_DAEMON_ENABLED`, default `False`)**: cutover flag for the always-on background daemon that keeps every heavy pipeline engine warm across cycles instead of a fresh `main_orchestrator.py` subprocess paying full import+construction cost every run (see `desktop/daemon_runtime.py`, `desktop/orchestrator_daemon.py`, `api/control_api.py`, `gui/daemon_client.py` above for the full architecture). `False` (the default) preserves today's exact subprocess behavior everywhere — fresh clones, CI, and other operators are unaffected until the flag is explicitly set. `True` switches BOTH: the desktop shell's always-on refresh loop (`desktop/engine_supervisor.start_engine`) spawns the daemon as a subprocess instead of `main.py --interval N`, and the Launcher tab's manual "Run Pipeline" button (`gui.orchestrator_runner.launch_orchestrator`) triggers a cycle over HTTP against the running daemon instead of spawning a new process. Enabling the daemon locally requires setting it in `.env` (`ORCHESTRATOR_DAEMON_ENABLED=true`) — NOT flipping the code default, which stays `False`. The Launcher tab's HTTP fast path additionally requires `ORCHESTRATOR_DAEMON_TOKEN` to be set (the Control API's `POST /run` is fail-closed by design — see `api/control_api.py` above); `ORCHESTRATOR_DAEMON_ENABLED` alone is enough for the always-on refresh loop (its internal timer calls `trigger_run()` in-process, never through the token-gated HTTP layer). **Operational note:** a stale/orphaned daemon process left holding `ORCHESTRATOR_API_PORT` (default 8601) causes a NEW daemon's own Control API bind to fail; the new daemon still starts (advisory pipeline unaffected) but logs a WARNING and its `output/daemon.json` write is delayed up to 5 s while it waits out a bounded readiness poll — check `lsof -i :8601` / `ps aux | grep orchestrator_daemon` if a fresh daemon launch seems slow to report ready, and kill any stale process before relaunching. **New env vars:** `ORCHESTRATOR_DAEMON_ENABLED`, `ORCHESTRATOR_DAEMON_TOKEN` (secret), `ORCHESTRATOR_API_PORT` (default 8601), `ORCHESTRATOR_INTERVAL_SECONDS` (default 0 = on-demand only; the daemon's own internal timer cadence, distinct from the `--interval` CLI flag which overrides it and distinct from `launch_daemon_engine`'s always-on-loop cadence). **Independent flag: `settings.PILOTS_API_ENABLED`** (default `False`) controls what the daemon PROCESS hosts once launched (the Pilots API alongside the Control API — see `desktop/orchestrator_daemon.py` above) — orthogonal to `ORCHESTRATOR_DAEMON_ENABLED`, which controls which subprocess the DESKTOP SHELL spawns in the first place. Running `python -m desktop.orchestrator_daemon` directly (e.g. for the Pilots PWA alone, without the desktop shell) honors `PILOTS_API_ENABLED` regardless of `ORCHESTRATOR_DAEMON_ENABLED`.
- **Durable pipeline run history (`desktop/run_history_store.py`)**: `OrchestratorDaemon._run_history` (see `desktop/daemon_runtime.py` above) is a plain in-memory ring capped at `run_history_size` (default 10) and lost on every daemon restart. `RunHistoryStore` gives each completed run cycle a second, durable home — a `pipeline_runs` SQLite/Postgres table resolved through `db_config.py`, matching `transactions_store.py`'s conventions (own `Base`, a `readonly=True` database-level read-only engine for consumers) — so the Pipeline Dashboard's run history can survive a restart. `OrchestratorDaemon._run_one_cycle` best-effort persists every completed `RunRecord` here immediately after building it (lazy import); a DB write failure only logs a warning and never affects the run's own SUCCEEDED/FAILED state. `api/control_api.py`'s `GET /runs/history?limit=` (read-token guarded, `limit` clamped `[1, 200]`, degrades to `[]` on a DB read failure) serves it independently of whether a daemon is currently attached — the whole point is to keep working across a restart. The webapp Pipeline screen (`webapp/src/screens/PipelineDashboard.tsx`) renders this as a separate "Full run history" section below the existing live (in-memory) "Run history" table, with a manual Refresh button plus an auto-refresh when an in-flight run completes. Only terminal (succeeded/failed) runs are ever written — a run still in flight only ever appears in the in-memory ring, never this table.
- **Command execution from the webapp Commands screen (`settings.COMMAND_EXECUTION_ENABLED`, default `False`)**: adds a new `"command"` `JobType` to the orchestrator Control API's `POST /jobs` (`api/_jobs.py`), letting the Pilots PWA's Commands screen actually RUN a manifest-listed CLI target instead of only composing/copying it for the operator to paste into their own terminal — layered on top of, not instead of, the existing `JOBS_API_ENABLED` + `ORCHESTRATOR_DAEMON_TOKEN` guard already protecting `POST /jobs` (both must ALSO be true; `COMMAND_EXECUTION_ENABLED=False` is the default and preserves today's compose-only behavior even if the other two are on). The `command`/`subcommand` params are resolved server-side via `pilots.commands.resolve_command` against the SAME committed `cli_introspect/command_manifest.json` artifact `GET /commands` already serves — the handler never trusts a client-supplied path/module string, only ever launching a target the manifest itself lists. `gui/orchestrator_runner.py::launch_manifest_command` builds argv from the resolved `CommandSpec`'s `invocation` field (splitting off the `python`/`python3` prefix and substituting `sys.executable`, exactly like every other launcher in this module) plus the caller-supplied `args` list appended literally (no shell involved, so argument values carry no shell-injection risk). Two safety carve-outs live in `launch_manifest_command`: `app_shell.py` is in `DISALLOWED_EXECUTE_COMMANDS` (it pops a native pywebview window on the server host, not something a browser click can show or use, so it stays copy-only and always raises `ValueError`); and `HIGH_STAKES_COMMANDS` maps `execution.kill_switch --activate`/`--deactivate` and `main.py --refresh-account` to a required, explicit `confirm=true` param on the job request — omitting it raises `ValueError` (mapped to HTTP 400) instead of silently running. `JobManager.start_job`'s single-flight check is narrowed for `JobType.COMMAND` to the SAME resolved command name (via the new `JobRecord.command_name` field) rather than the job type as a whole, so two different manifest targets can run concurrently while a duplicate invocation of the identical command still 409s. Deliberately excluded from `gui/env_io.py`'s `ALLOWED_KEYS`/`SECRET_KEYS` (hand-set in `.env` only) — same treatment as `BROKERAGE_CONNECT_ENABLED` — because this flag gates execution of the global kill switch, a forced Robinhood re-login, and arbitrary flags to the orchestrators, a materially bigger risk than the fixed-dispatch `JOBS_API_ENABLED` alone already covers. - **ETF volatility-transmission sizing derate (`risk/etf_transmission.py`, `settings.ETF_TRANSMISSION_SIZING_ENABLED` default `False`)**: Ben-David, Franzoni & Moussawi (2018, *JF*) — ETF arbitrage transmits a shock in one constituent to its otherwise-healthy peers, so a heavily ETF-wrapped name carries extra non-fundamental, non-diversifiable variance that neither `sizing/kelly.py` nor `sizing/vol_target.py` can see (both observe only a single name's own return series). The multiplier is `transmission_multiplier(ownership_pct, comovement_r2, *, max_derate, ownership_reference, floor)`: explicit, monotone non-increasing in both arguments, bounded to `[floor, 1.0]`, two knobs, no fitted parameters. **Three invariants:** (1) the derate is EXCLUDED from `was_capped`/`binding_constraint` — it is continuous signal-driven derating, not a hard-ceiling event, exactly as for `Regime_Multiplier`, and folding it in would fire the guardrail on every ETF-heavy name and drown out genuine ceiling events in `sizing/cap_audit_store.py` and the `SIZING_CAP_ALERT_THRESHOLD_PCT` alert; it is surfaced as its own `SizingDecision.etf_transmission_multiplier` field instead. - **ETF-transmission-adjusted portfolio covariance (`risk/etf_transmission.py::build_transmission_adjusted_cov`, `settings.ETF_TRANSMISSION_PORTFOLIO_ENABLED` default `False`)**: the per-name derate above cannot see the mechanism's actual claim — ETF arbitrage raises CO-MOVEMENT between co-held names, a portfolio-level effect — so this feeds `apply_portfolio_gross_cap()`'s EXISTING `cov_matrix`/`target_vol` risk-aware path (unreachable from production until the "Reduction-only guarantee" fix above) with an ETF-co-ownership-inflated covariance matrix, rather than a second portfolio-cap mechanism. `cov_adj[i,j] = cov[i,j] * (1 + inflation * overlap[i,j])` for `i != j` ONLY — the diagonal is never touched, since per-name variance is already the derate's job. `overlap[i,j]` (`_pairwise_etf_overlap`) is cosine similarity, in `[0, 1]`, of two symbols' ETF-basket weight vectors. **PSD repair is mandatory**: multiplicative off-diagonal inflation is not guaranteed to preserve positive semi-definiteness, and `portfolio_vol_target` has no PSD check of its own — an indefinite matrix would saturate the leverage scalar at `max_leverage`, levering the book up on a broken risk estimate; `_nearest_psd` eigenvalue-clips up to a floor (see below) and reconstructs. **Never a partially-covered matrix**: `portfolio_vol_target` ZEROES OUT any symbol missing from `cov_matrix` (its own correct behavior for unknowable risk, but far harsher than the sum-of-|weight| fallback this replaces), so `pipeline/production_steps.py::_build_etf_transmission_cov_matrix` insists on FULL coverage across the cycle's universe before returning anything but `None`; any gap degrades the whole cycle back to `cov_matrix=None`. `target_vol` reuses the existing `settings.VOL_TARGET` rather than a redundant new setting. Three bounds: minimum issuance spacing (`GDELT_MIN_REQUEST_INTERVAL_SECONDS`, default 5.0, lock held across the sleep), retry with exponential backoff honouring `Retry-After` (`GDELT_MAX_RETRIES` 2, `GDELT_RETRY_BACKOFF_SECONDS` 5.0), and a cooldown circuit breaker that SKIPS GDELT calls outright for `GDELT_COOLDOWN_SECONDS` (300) after `GDELT_COOLDOWN_THRESHOLD` (3) consecutive FAILED requests — 429, 5xx, or transport error alike — the bound that keeps an unresponsive host from turning a long backfill into hours of certain-to-fail requests while EDGAR/Finnhub/Reddit starve for wall-clock budget. - **Strategy validation harness genuine-OOS gate (`validation/harness.py`, `validation/metrics.py`, `settings.VALIDATION_HARNESS_OOS_GATE_ENABLED` default `False`, 2026-07 quant-integrity fix)**: `ValidationReport.sharpe`/`.max_dd`/`.sortino`/`.calmar`/`.hit_rate`/`.avg_trade_pct`/`.turnover` — everything feeding the `deployable` gate's `Sharpe > 0.5` / `MaxDD < 30%` criteria besides PBO/DSR — were computed from `self.strategy_fn(X, y, X, y)`, an in-sample "test" set identical to the training set, while only PBO/DSR were genuinely out-of-sample (via `CombinatorialPurgedCV`); separately, CPCV's own PBO/DSR Sharpes were computed on gross (cost-free) returns even though the in-sample leg applied `_apply_cost_model`'s turnover-scaled cost — an inconsistent cost basis between the gate's two halves. `run_cpcv_evaluation()` gained an optional `cost_model_fn` parameter (cost-adjusts every CPCV path's returns before any Sharpe/PBO/DSR/drawdown statistic) plus four new genuinely-OOS aggregates (`mean_oos_max_dd`/`mean_oos_sortino`/`mean_oos_hit_rate`/`mean_oos_avg_trade_pct`/`mean_oos_turnover` — the mean of each metric computed independently per CPCV path, not one concatenated curve, since CPCV's combinatorial test-block reuse across paths would double/triple-count dates in a naive concatenation). When the settings flag is `True`, the harness wires its cost model into CPCV and replaces the seven in-sample numbers with these OOS aggregates; `equity_curve`/`benchmark_curve`/`macro_benchmark_curve` stay on the full-sample series either way (a single non-overlapping OOS equity curve needs the AFML CPCV backtest-path-recombination algorithm, not implemented here — a real, separate follow-up, not silently faked). Default `False` reproduces every currently-recorded `docs/VALIDATION_STRATEGY_FIX_LOG.md` PBO/DSR/Sharpe/MaxDD baseline exactly — this sandboxed dev/CI environment has no live-market network access to re-verify the registered `STRATEGY_REGISTRY` fleet against the corrected numbers. `n_trials` (already persisted per-strategy but never displayed) is now also surfaced next to DSR in the main HTML validation report and the GUI Validation Lab table.
