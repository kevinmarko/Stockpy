# Settings/flags audit → fix drift, build a "Settings Reference" explainer, expose a hand-picked subset

**Workflow note**: this is a two-phase, two-agent-fleet plan. **Antigravity builds it** (8 parallel agents, one per work package below). **Claude Code (this session or a follow-up one) audits the result** (6 parallel agents, one per audit dimension below) once Antigravity reports done. This file is written to be handed to Antigravity as its implementation plan artifact (per this repo's own convention of committing a plan under `.claude/` on the feature branch) and then reused as the audit brief afterward.

## Context

The operator asked: are we missing any flags in the webapp UI, and can we build an explainer for how each flag affects the platform. A 3-agent audit of `settings.py` (464 pydantic fields), `shared/env_io.py`/`settings_keysets.py` (GUI-write governance), the webapp's 8 `/settings/*` editors, and the existing help-content infrastructure found:

- **Governance is complete**: every field is already classified into `ALLOWED_KEYS`/`SECRET_KEYS`/`EXCLUDED_FROM_GUI` (CI-enforced via `tests/test_gui_env_io.py::test_every_settings_field_is_classified`, zero gaps). Nothing is "secretly" ungoverned.
- **UI coverage is not**: only ~229 of 464 fields are reachable through any webapp screen. The remaining ~235 non-secret fields — including real, actively-read automation toggles like `OPTIONS_0DTE_ENABLED`, `OPTIONS_DELTA_HEDGE_ENABLED`, `PAPER_OPTIONS_AUTO_EXECUTE_ENABLED`, and the whole `CIRCUIT_BREAKER_*` risk subsystem — are `.env`-hand-edit-only today.
- **The explainer content mostly already exists and is unused**: 442 of 464 fields already carry a human-written `Field(description=...)` in `settings.py`. It's already piped live into the 8 existing editors as each field's hint text (`_build_groups_payload()` → `TunableField.description` → `GenericSettingsEditor`'s `FieldRow`). It just isn't surfaced for the ~235 fields with no editor, and there's no single place to browse/search all of it.
- **Two concrete bugs, independent of the bigger gap**: (1) `webapp/src/api/mock.ts`'s Feature Flags fixture is missing 11 real flags the live backend registry has (`OFI_SHIELD_ENABLED`, `BROKER_BACKEND`, `LIVE_TRADE_EXECUTION_ENABLED`, `LIVE_TRADE_APPROVAL_ENABLED`, `PAPER_TRADES_BRIDGE_TO_TRANSACTIONS_ENABLED`, `MCP_OAUTH_MULTI_USER_ENABLED`, `FORECAST_BACKFILL_ENABLED`, `JULES_ENABLED`, `PAPER_BROKER_WRITES_ENABLED`, `FIX_GATEWAY_ENABLED`, `PIPELINE_STALL_ALERT_ENABLED`) — mock-mode development doesn't exercise what live actually returns. (2) `helpContent.ts` already has a written `"settings-feature-flags"` `TAB_HELP` entry that is never rendered anywhere — `FeatureFlagsScreen.tsx` and the 3 other `GenericSettingsEditor`-based screens (`SettingsManager`/Tunables, `SettingsCacheLongShort`, `SettingsPaperBroker`) render no `TabGuide` at all.
- One genuinely dead flag was found in passing: `docs/settings_liveness.json` classifies `OPTIONS_EARNINGS_CRUSH_ENABLED` as `no_op` — it is read nowhere in production code. It must not be promoted into any new editable group (that would be a UI lying about effect); it's flagged honestly instead.

Operator decisions from this session: build the full read-only reference screen (not just the bug fixes), **and** promote a hand-picked, well-justified subset of the currently-unexposed fields to real editable Tunables groups rather than leaving all ~235 read-only forever.

Per CLAUDE.md's Branch Workflow, this goes through a feature branch + PR (it touches `api/pilots_api.py` and exposes real automation toggles — not eligible for the low-risk direct-to-main path), with an Implementation Plan committed to `.claude/` before code, and a task tracker + walkthrough committed alongside the PR, all under a unique feature-scoped name (e.g. `settings_reference_implementation_plan.md`, `settings_reference_task.md`, `settings_reference_walkthrough.md` — never a bare `plan.md`/`task.md`).

## Phase 1 — Antigravity build (8 parallel work packages)

Branch: one feature branch, lowercase-kebab (e.g. `settings-reference-explainer`). Work packages 1–2 have no dependency on the rest and can land as an early, small first commit/PR if Antigravity's orchestration prefers to ship the bug fixes fast; 3–8 depend on each other in the order listed (3 before 6, 4/5 before 7, 3–7 before 8). Every field promoted anywhere in this plan must be double-checked against `docs/settings_liveness.json` before being called editable — the `OPTIONS_EARNINGS_CRUSH_ENABLED` `no_op` finding is the concrete reason why.

**WP1 — Fix Feature Flags mock/live parity bug**
`webapp/src/api/mock.ts`: add the 11 missing keys to `FEATURE_FLAGS_TUNABLE_DEFS` with correct type/default, matching the live registry (`pilots/feature_flags.py`'s `WRITE_GATE_REASONS`/`DIAGNOSTIC_FLAG_REASONS` + `settings_keysets.DANGEROUS_KEYS`). Add a regression test asserting the mock's key set is a superset of `FEATURE_FLAG_KEYS` so this can't silently reappear.

**WP2 — Wire up the orphaned TabGuide + add missing ones**
Add an optional `tabGuideKey?: string` prop to `webapp/src/components/GenericSettingsEditor.tsx` that renders `<TabGuide tabKey={tabGuideKey} />` above the form when supplied (one shared implementation point instead of duplicating the render call per wrapper screen). Wire `tabGuideKey="settings-feature-flags"` into `FeatureFlagsScreen.tsx` (content already exists in `helpContent.ts`). Author 3 new `TAB_HELP` entries (`"settings-tunables"`, `"settings-cache-long-short"`, `"settings-paper-broker"`) and wire them into `SettingsManager.tsx`, `SettingsCacheLongShort.tsx`, `SettingsPaperBroker.tsx`. Check `SentimentSettings.tsx`/`SectorSelectionSettings.tsx`/`FmpSettings.tsx`/`EtfTransmissionSettings.tsx` for the same gap and fix if found.

**WP3 — Backend: `GET /settings/reference` endpoint**
New dependency-light module `pilots/settings_domains.py` (stdlib/`settings_keysets`-only, no heavy-engine imports — this repo's `pilots/` AST import guard applies, see `tests/test_pilots_strategy_matrix.py`) with a static `KEY_DOMAIN: dict[str, str]` mapping every `settings.py` field to one of ~14 domain labels (Financial/Risk/Sizing, Execution/Brokers, Options Desk, Market Data/DB, Universe/Watchlist, Forecasting/ML, ETF Transmission, Sentiment/News/Attention, AI/LLM/RAG, Orchestrator/Daemon/Jobs, Alerting/Observability, Strategy Overlays, Filesystem/Bootstrap, RLHF) — a prefix heuristic plus an explicit override list for cross-cutting names, not 464 hand-typed lines. New endpoint `GET /settings/reference` in `api/pilots_api.py`, `require_read_token`-gated like the other `/settings/*` GETs. For every `Settings.model_fields` entry, return `key`, `category` (`secret`/`excluded`/`allowed`, from `shared.env_io`'s three sets), `value` (masked `"•••• (set)"`/`"(not set)"` for secrets, real value otherwise — CONSTRAINT #4, never leak a secret), `default`, `type`, `description` (the field's own `Field(description=...)`, `null` if absent — never fabricated), `domain`, `dangerous`, `liveness` (reuse `pilots/settings_meta.py::field_metadata()` as-is — do not reimplement), and `editable_at` (the route of whichever existing `/settings/*` editor already exposes this key, `null` if none — a reverse index over the 8 existing `_*_GROUPS` literals, built once at import time the same way `_build_feature_flags_index()` already does). Backfill `Field(description=...)` for the ~22 fields in `settings.py` currently missing one (non-behavioral, comment-only diffs).

**WP4 — Backend: "Options Desk Automation" Tunables group**
Add a new group (13 fields) to `_TUNABLE_GROUPS` in `api/pilots_api.py`: `PAPER_OPTIONS_AUTO_EXECUTE_ENABLED`, `OPTIONS_AUTO_EXIT_ENABLED`, `OPTIONS_PROFIT_TARGET_PCT`, `OPTIONS_STOP_LOSS_MULTIPLE`, `OPTIONS_MANAGE_DTE_THRESHOLD`, `OPTIONS_DELTA_HEDGE_ENABLED`, `OPTIONS_DELTA_HEDGE_BAND_SPY_SHARES`, `OPTIONS_0DTE_ENABLED`, `OPTIONS_0DTE_PROFIT_TARGET_PCT`, `OPTIONS_0DTE_STOP_LOSS_PCT`, `OPTIONS_0DTE_HARD_EXIT_TIME`, `MAX_OPTION_NOTIONAL_PER_TRADE`, `MAX_CONCURRENT_OPTION_POSITIONS`. **Do not include `OPTIONS_EARNINGS_CRUSH_ENABLED`** (confirmed `no_op`). None require `DANGEROUS_KEYS` confirmation — consistent with the existing `PAPER_BROKER_WRITES_ENABLED` precedent ("no real money or broker is involved"), which applies identically to every field in this group (all paper-only).

**WP5 — Backend: "Circuit Breaker" group + misc fold-ins**
New "Circuit Breaker" Tunables group (6 fields): `CIRCUIT_BREAKER_ENABLED`, `CIRCUIT_BREAKER_VOLATILITY_Z_THRESHOLD`, `CIRCUIT_BREAKER_VPIN_THRESHOLD`, `CIRCUIT_BREAKER_OFI_THRESHOLD`, `CIRCUIT_BREAKER_LOSS_VELOCITY_WINDOW_MINS`, `CIRCUIT_BREAKER_REFERENCE_SYMBOL`. Fold 6 more into existing groups: `MULTIFACTOR_MICROCAP_THRESHOLD`, `CORRELATION_CLUSTER_LOOKBACK_DAYS`, `CORRELATION_CLUSTER_THRESHOLD`, `FEATURE_DRIFT_PSI_ENABLED` → Financial Constants/Validation Gates; `DAEMON_SHUTDOWN_TIMEOUT_SECONDS`, `PIPELINE_STALL_ALERT_SECONDS` → Runtime & Ops. Add `MULTI_BROKER_GATEWAY_ENABLED` to `pilots/feature_flags.py::WRITE_GATE_REASONS` (it gates a real execution capability — belongs there, not in Tunables).

**WP6 — Frontend: Settings Reference screen**
New types `SettingsReferenceField`/`SettingsReferenceResponse` in `webapp/src/api/types.ts`; `api.getSettingsReference()` in `client.ts`; a `mock.ts` fixture that is a representative multi-domain sample (not a hand-typed copy of all 464 rows — comment explaining why, to avoid recreating WP1's exact drift risk at 10x the scale). New screen `webapp/src/screens/SettingsReference.tsx` at `/settings/reference`: domain-grouped, searchable/filterable, read-only. Each row: key, description, default, current value (secrets show only the masked string), a liveness badge (immediately/next-restart/no-effect — a `no_op` field gets an explicit "not read anywhere — changing it has no effect" callout), and an "Edit here →" link to `editable_at` when non-null. Add a `"settings-reference"` `TAB_HELP` entry + `TabGuide` explaining scope. Link the new screen from `SettingsModules.tsx`'s hub.

**WP7 — Frontend: mock parity for promoted fields + tests**
Update the Tunables mock fixture in `mock.ts` to include the ~25 fields WP4/WP5 promoted. Write `SettingsReference.test.tsx` (render, search, domain filter, secret masking, no-op badge, edit-elsewhere link) and extend `SettingsManager`/Tunables tests for the two new groups.

**WP8 — Docs + backend tests**
- `docs/architecture/webapp-and-gui.md`: new `/settings/reference` endpoint+screen, the new Tunables groups, the TabGuide/mock-parity fixes.
- `docs/HOW_TO_GUIDE.md`: short new section under Settings introducing the Settings Reference browse feature.
- `CLAUDE.md` (auto-synced to `AGENTS.md` by the existing sync hook): a new dated bullet documenting the newly-exposed settings, the new reference endpoint/screen, and the two fixed drift bugs, following this file's existing "New settings default to X" bullet convention.
- Backend tests (`tests/test_pilots_api.py` or a new `tests/test_settings_reference.py`): auth gating, secret masking, every one of the 464 fields appears exactly once, `editable_at` correctness for a few known keys, and a **guardrail test asserting none of the newly-added Tunables keys classify as `no_op`** in `docs/settings_liveness.json` (prevents repeating the `OPTIONS_EARNINGS_CRUSH_ENABLED` mistake for any future addition). Extend the Feature Flags registry test for `MULTI_BROKER_GATEWAY_ENABLED`.

## Phase 2 — Claude Code audit (6 parallel agents, run after Antigravity reports done)

Once Antigravity's branch/PR is ready, spawn 6 agents in parallel, each independently verifying one dimension against the actual diff (not against Antigravity's own claims):

1. **Honesty audit (CONSTRAINT #4/#6)** — `honesty-auditor` agent on the new `GET /settings/reference` endpoint and `pilots/settings_domains.py`: secret masking never leaks a real value, no fabricated/guessed descriptions, `no_op` fields correctly flagged (not silently omitted or mislabeled), `pilots/settings_meta.py::field_metadata()` reused rather than reimplemented/duplicated.
2. **Mock/live parity audit** — `api-parity-reviewer` agent (or general-purpose doing the same job) on the full webapp diff: the new Settings Reference mock, the extended Tunables mock, and the Feature Flags mock fix from WP1 — confirm mock and live actually agree in shape and (where the fixture claims completeness) in key-set.
3. **Completeness/coverage audit** — confirm every one of the 464 `settings.py` fields appears exactly once in the reference endpoint's output, domain assignment is sane (no field left in a junk-drawer default domain unless genuinely uncategorizable), and `editable_at` correctly cross-references every existing editor plus the two new Tunables groups.
4. **Promotion-correctness audit** — for each of the ~25 newly-promoted fields: confirm it is genuinely non-secret/non-dangerous per `shared/env_io.py`/`settings_keysets.py`, confirm it is NOT `no_op` per `docs/settings_liveness.json` (the exact mistake this plan is designed to avoid), confirm `OPTIONS_EARNINGS_CRUSH_ENABLED` was excluded and the exclusion is documented (not silently dropped, not accidentally included).
5. **End-to-end webapp verification** — actually run the dev server (mock mode, then live if feasible) and exercise: Settings Reference screen search/filter, secret-value masking, the previously-orphaned `TabGuide` panels now rendering, the new Tunables groups appearing and saving correctly. Screenshot/console-check per this repo's "actual browser check, not just typecheck" verification rule.
6. **Docs & test-suite audit** — confirm `docs/architecture/webapp-and-gui.md`, `docs/HOW_TO_GUIDE.md`, and `CLAUDE.md`/`AGENTS.md` were actually updated and stayed in sync, and that `make verify`/`pytest` and `npm run --prefix webapp typecheck`/`npm test` were actually run and shown green — not merely asserted in the walkthrough.

Report findings from all 6 agents together; anything CONFIRMED gets fixed before merge (own commits on the same branch, not a rewrite of Antigravity's history unless a conflict requires it — per CLAUDE.md's branch-workflow rules on amending others' commits).
