# Architecture: Signal & Calculation Engines

> Part of the split-out `CLAUDE.md` System Architecture reference. See [../../CLAUDE.md](../../CLAUDE.md) for the index.

- **processing_engine.py** — vectorized fundamental valuations (Graham Number, Gordon Fair Value) and technical indicators (RSI, MACD, Aroon, ATR, SMA). Iterative loops/`.iterrows()` over price series are disallowed; everything must be expressed as pandas/numpy vector operations. **Tier 2.3 Phase 3 wiring**: `calculate_fundamental_metrics()` initialises a `HistoricalStore` instance when `settings.HISTORICAL_STORE_ENABLED=True` and calls `get_fundamentals(ticker, max_age_days=settings.FUNDAMENTALS_REFRESH_DAYS)` to serve cached fundamentals or write fresh ones; the typed return dict is overlaid onto the raw `info` dict before existing downstream calculations (no key-mapping changes in downstream code). `HistoricalStore` is imported lazily (inside the method body) to avoid circular imports. **Rolling beta (2026-07):** module-level `calculate_rolling_beta(price_df, spy_df, window=60) -> pd.Series` computes a TIME-VARYING beta (`.rolling(window).cov(spy_returns) / .rolling(window).var()`, inner-joined by date) — distinct from the existing STATIC single-window `Beta` column (`data/yahoo_fundamentals.py`, surfaced via `config.COLUMN_SCHEMA`), which stays unchanged (FMP is now the primary fundamentals provider via `data/fmp_fundamentals.py` / `FUNDAMENTALS_SOURCE=fmp`, with Yahoo as fallback). Naturally lookahead-free by construction (verified by two perturbation tests in `tests/test_indicators_lookahead.py` — perturbing either the ticker or the SPY series after a cutoff leaves the beta value at that cutoff unchanged); the first `window` rows are `NaN`, never fabricated. No new `COLUMN_SCHEMA` entry (a rolling series doesn't fit one dashboard cell) — surfaced instead as an on-demand chart in the GUI Analytics tab (`gui/panels/analytics.py::_render_rolling_beta_chart`, computed from `HistoricalStore`-cached bars for the selected symbol and SPY). **Degenerate-std guard (2026-07):** `calculate_technical_metrics()`'s Sortino computation (feeding the live `Sortino_Ratio` column) had its `downside_std > 0` guard hardened to `>= 1e-12`, matching the repo-wide convention documented in `CLAUDE.md`.
- **macro_engine.py** — macroeconomic regime detection/gating. `MacroEngine.__init__` now constructs a persistent `regime.hmm_regime.HMMRegimeDetector(n_states=settings.HMM_N_STATES, retrain_freq_days=settings.HMM_RETRAIN_FREQ_DAYS, covariance_type=settings.HMM_COVARIANCE_TYPE, n_iter=settings.HMM_N_ITER, tol=settings.HMM_TOL)` instance (`self._hmm_detector`). `compute_hmm_risk_on_probability(spy_price_df)` builds the feature matrix via `regime.hmm_regime.build_feature_matrix()` (supporting optional credit spread `BAMLH0A0HYM2` via `settings.HMM_CREDIT_SPREAD_FEATURE_ENABLED` and 20D-60D vol term structure via `settings.HMM_VOL_TERM_SPREAD_FEATURE_ENABLED`) and returns a dict containing the HMM's regime probabilities, state label, and `risk_on_probability` second opinion — or `None` (never fabricated) if SPY history, macro history, or the aligned feature matrix (`< HMM_MIN_FIT_ROWS=100` rows) is insufficient, or if fit/predict raises (logged, never propagated — a statistical second opinion failing must never crash the primary rules-based pipeline). **Tier 2.3 Phase 3 wiring**: when `settings.HISTORICAL_STORE_ENABLED=True`, `compute_hmm_risk_on_probability` routes the VIXCLS, T10Y2Y, and optional BAMLH0A0HYM2 series through `HistoricalStore.get_macro(...)` (with `data_engine=self.data_engine` as the top-up source) instead of calling `self.data_engine.fetch_macro_history()` directly. On any HistoricalStore failure the code falls back to the direct `DataEngine.fetch_macro_history()` call (pre-Phase-3 behavior). The single-snapshot `_build_macro_dto` path (current-state reads for the kill-switch) is NOT routed through HistoricalStore — only the HMM's historical series benefit from DB caching.
- **regime/hmm_regime.py** — Gaussian HMM regime detector (Hamilton 1989), a statistical second opinion to the rules-based regime in `macro_engine.py`. `build_feature_matrix(spy_price_df, vix_series, yield_curve_series, credit_spread_series=None, include_vol_term_spread=False)` builds the feature matrix (`spy_return`, `realized_vol_20d`, `vix_level`, `yield_curve_spread`, plus optional `credit_spread` and `vol_term_spread`), normalizing all series indices to timezone-naive, time-stripped dates before aligning (yfinance is often tz-aware/intraday-stamped; FRED is naive/midnight — without this, misaligned sources silently produce an all-NaN join). `HMMRegimeDetector(n_states=3, retrain_freq_days=7, covariance_type='diag', n_iter=150, tol=1e-4)`: `fit(features_df)` refits only if `retrain_freq_days` have elapsed since the last real fit (expanding window is the caller's responsibility — pass progressively more history each call); within that window, repeated `fit()` calls are no-ops, which is exactly what `tests/test_hmm_no_lookahead.py` exercises. `identify_states_by_vol()` sorts states by fitted variance (trace calculation for `full` covariance, diagonal variance for `diag`, spherical variance, or feature-mean norm for `tied`) ascending and labels `["bull", "sideways", "bear"]`. `predict_proba(features_df)` returns a dictionary containing FORWARD (filtered) state probabilities, dominant state, state label, and risk-on probability at the LAST ROW only of whatever's passed in — never Viterbi/smoothing — via the mathematical identity that a smoothed posterior's last row in any sequence equals pure forward filtering (the backward pass is seeded with `beta_T=1` at the sequence's own terminal step, so there is no "future" to smooth with). `compute_diagnostics(features_df)` computes AIC, BIC, Log-Likelihood, transition probabilities, expected regime durations, and empirical return/volatility metrics per state. `validation/regime_diagnostics.py` and `scripts/audit_regime_model.py` provide full walk-forward regime backtesting and model comparison tooling. See [`docs/regime_model_tuning_guide.md`](../regime_model_tuning_guide.md) for the theoretical foundation, hyperparameter definitions, and walk-forward tuning methodology.
- **technical_options_engine.py** — options-specific technical metrics (IV rank, GARCH vol, options IV edge). **Premium directive helper**: top-level `build_premium_directive(symbol, bars, *, spot_price, is_stale=False, target_dte=30, macro_dto=None, vrp=None, risk_free_rate=settings.RISK_FREE_RATE) -> dict` fuses GJR-GARCH σ, realized-vol IVR proxy, Aroon+Coppock trend bias (via the deterministic `_determine_trend_bias` rule), full ATM Black-Scholes Greeks, and the deterministic strategy directive from `OptionsPricingRecommender.generate_strategy_pricing_matrix` into a single hydrated row (Symbol, Price, Stale, Sigma_GARCH, IVR_Proxy, True_IVR, Aroon_Oscillator, Coppock_Curve, Trend_Bias, Strategy, Action, Net_Premium, Realizable_Daily_Theta, ATM_{Delta,Gamma,Vega,Theta_Daily}, Short_/Long_Strike, Short_/Long_Delta, Legs, Integrity_OK, Integrity_Issues). NaN — never fabricated zeros — when a primitive can't be computed (CONSTRAINT #4). Centralised here (not duplicated in `gui/panels.py`) so the Gravity AI Review Suite exercises the same code path the GUI does. **Integrity validator**: `validate_directive_integrity(directive, *, delta_tolerance=0.05, strike_grid=STRIKE_GRID_USD=0.50) -> {"ok": bool, "issues": [str], "checks": [dict]}` asserts every leg strike lies on the `$0.50` exchange grid and (when a `Delta` is present on the leg dict) the resolved BS delta is within `delta_tolerance` of the conventional target in `EXPECTED_DELTA_TARGETS` (Put Credit Spread ±0.30/±0.15, Iron Condor ±0.16/±0.05, etc.). Cash/Wait directives pass trivially; Iron Condor legs omit `Delta` by engine convention and the validator skips (never fabricates) that check. **Real True_IVR, opt-in (`settings.OPTIONS_TRUE_IVR_ENABLED`, default `False`, 2026-07):** closes the gap between the two IVR code paths this codebase carried — a real, options-chain-derived True_IVR previously existed ONLY inside `main_orchestrator.py`'s `pipeline/production_steps.py::OptionsAnalysisStep` (which calls `volatility.iv_engine.get_30d_atm_iv()` + `calculate_true_ivr()` against its own `IVHistoryStore`), while `build_premium_directive` — the code path used by the GUI Technical Options Matrix tab, the `get_options_directive` MCP tool, `api/metrics_api.py`, and `execution/options_queue_builder.py` — computed only the realized-vol-only `IVR_Proxy`, with its own docstring/comment honestly disclaiming "true IVR requires an options chain." When the flag is on, `build_premium_directive` now ALSO attempts the same real computation `OptionsAnalysisStep` does: it fetches a live 30-calendar-day ATM IV via `get_30d_atm_iv()` and ranks it via `calculate_true_ivr()` against the SAME on-disk `iv_history` table (`IVHistoryStore`) `OptionsAnalysisStep` already writes to — so a live pipeline that has been running populates history this on-demand path can immediately benefit from; a fresh environment or one where the orchestrator has never run stays `NaN` until it warms up (strictly-prior-day ranking, never a lookahead). **Data-engine sourcing decision**: `data/market_data.py`'s `CompositeProvider` (the convention-mandated provider for GUI/MCP-path quote/bar/fundamentals fetches) exposes NO chain-shaped method at all — extending its `MarketDataProvider` ABC with a chain fetch to satisfy one opt-in feature would be a large, unjustified surface increase, so `build_premium_directive` instead constructs a fresh, lightweight `data_engine.DataEngine(fred_api_key="")` scoped to just this one call (its `__init__` does zero network I/O with no FRED key; only `fetch_options_chain()` touches the network) — the least-invasive move that mirrors exactly what `OptionsAnalysisStep` already does rather than inventing a second, competing convention. Both `data_engine`/`iv_history_store` are injectable kwargs (mainly for tests); `true_ivr_enabled` is a tri-state override (`None` reads the live setting) and `as_of_date` defaults to `bars.index[-1]`. **Never replaces, always adds**: the row carries BOTH `IVR_Proxy` (untouched) and the new `True_IVR` key so provenance stays honest; `generate_strategy_pricing_matrix`'s `true_ivr` argument prefers `True_IVR` over `IVR_Proxy` only when the flag is on and a finite value was actually computed, falling back to `IVR_Proxy` exactly as before otherwise. Any failure at any step (no chain data, empty/warm-start history, a network error, or any exception) degrades to `float('nan')` and never crashes or changes the existing `IVR_Proxy`-driven Cash/Wait fallback (CONSTRAINT #4/#6). `False` (the default) is byte-identical to pre-flag behavior — zero new network calls, zero new DB reads, `True_IVR` always `NaN`. Surfaced in the GUI Technical Options Matrix tab's column order and in the `get_options_directive` MCP tool's markdown + JSON payload (`true_ivr`), both with tooltip/caption text sourced from `gui/help_content.py` (`METRIC_HELP["True_IVR"]`, `SECTION_HELP["options.matrix_methodology"]`) rather than hardcoded prose. **Caveat**: there is no way to backfill REAL historical IV for the warm-start period itself (that would need historical options-chain data this platform doesn't have) — real ranking only accrues going forward from whenever the flag is first enabled and a chain fetch first succeeds, on either code path, for a given ticker. Tests: `tests/test_options_matrix.py` (flag-off byte-identical, flag-on with a populated in-memory `IVHistoryStore` fixture, flag-on with empty history degrading to NaN, chain-fetch exception degrading to NaN without crashing the Cash/Wait fallback).
- **forecasting_engine.py** — ARIMA, Monte Carlo, Holt-Winters, Prophet, and CNN-LSTM forecasts. Deterministic trend params are enforced (`trend='t'` for ARIMA, `trend='add'` for Holt-Winters) and Monte Carlo uses structural drift (μ − 0.5σ²) to prevent naive flatline projections. The CNN-LSTM model implements direct multi-horizon forecasting, trains once per ticker, and uses strict train-only scaler fitting and sequence creation to eliminate lookahead bias. **Purged internal train/val split (2026-07 quant-integrity fix):** `make_direct_multistep_windows`'s stride-1 windows overlap by `lookback-1` raw rows, so Keras's own `validation_split=0.2` (used to drive `EarlyStopping`) left the last training windows near-duplicates of the first validation windows, optimistically biasing `val_loss`-based epoch selection. `ForecastingEngine.purged_train_val_split` (mirrored, pure-numpy, in `cnn_lstm_worker.py::_purged_train_val_split` for the subprocess-isolated path) purges those overlapping windows and passes an explicit `validation_data=(X_val, Y_val)` instead — applied unconditionally (not a settings-gated opt-in; this only affects which epoch's weights `EarlyStopping(restore_best_weights=True)` selects, not the causal correctness of the emitted forecast itself, which `fit_scalers_on_train`'s train/reserve boundary already guaranteed). Tests: `tests/test_forecasting_lookahead.py::TestPurgedTrainValSplit`, `tests/test_cnn_lstm_worker.py`. **GARCH → Monte Carlo sigma (2026-07):** the Monte Carlo σ is now sourced from the GJR-GARCH(1,1) estimator (`technical_options_engine.estimate_gjr_garch_volatility`, forward-looking + fat-tailed) via the new `ForecastingEngine._estimate_daily_sigma(history_df, fallback_daily_sigma)` helper, instead of a naive historical log-return stdev — making the Monte Carlo bands regime-responsive (they widen in turbulent vol regimes and tighten in calm ones). **SCALE RULE (do NOT "fix"): GARCH returns ANNUALIZED vol; Monte Carlo needs DAILY, so `_estimate_daily_sigma` divides by `sqrt(252)` — mandatory, because `run_monte_carlo`'s auto-normalize guard only inspects `mu`, so it cannot detect/correct an annualized σ.** Degrades to the historical daily std (never raises) when GARCH is unavailable / `history_df is None` / `< 22` rows / the flag is off. Behind `settings.FORECAST_USE_GARCH_SIGMA` (default `True`). **Prophet → ensemble (2026-07):** `run_prophet_forecast`'s h=30 output (previously computed but discarded from the blend) now enters `model_forecasts["prophet"]` at the h=30 horizon ONLY and is folded into `_blend_with_skill`'s static branch as a backward-compatible overlay `final = base*(1-w) + prophet*w`, `w = settings.FORECAST_PROPHET_WEIGHT` (default 0.25, clamped to [0,1]). Prophet still runs at most once per call; Prophet-absent behavior is byte-identical to the pre-overlay blend. **Fit-once hot-loop refactor (2026-07):** `run_arima`/`run_holt_winters_grid_search` are split into fit-once + forecast helpers (`run_arima_fit`/`forecast_from_arima_fit`, `run_holt_winters_fit`/`forecast_from_hw_fit`); `generate_forecast` now fits ARIMA and Holt-Winters exactly ONCE per ticker (both fits are horizon-independent) and reuses each fitted model across the target-days forecast AND every horizon in `[10,30,60,90]`, collapsing ~5 ARIMA + ~12-15 HW statsmodels fits/ticker down to 1 + 3. Output is byte-identical to the pre-refactor per-horizon path (verified by shim-equality + fit-count tests in `tests/test_forecasting_engine.py`); the old `run_arima`/`run_holt_winters_grid_search` names are retained as back-compat shims (fit-once + forecast-once internally). CNN-LSTM (direct multi-step, trained once) and Prophet (h=30, run once) were already single-fit and are unchanged. **GARCH double-fit elimination (2026-07):** `generate_forecast` gained `precomputed_garch_annual_vol: Optional[float] = None`; when supplied, `_estimate_daily_sigma` uses `precomputed_garch_annual_vol / sqrt(252)` (the same SCALE RULE) instead of running a SECOND internal GJR-GARCH fit. `main_orchestrator.py` (~line 410) passes `dashboard_df['GARCH_Vol']` — the per-ticker GJR-GARCH vol it already fit once earlier in the cycle (~line 300) — so no ticker is GARCH-fit twice per cycle; `main.py`/`engine.advisory` callers pass nothing (default `None` → unchanged internal fit). **Skill-weighted blend now operator-activatable (2026-07-09):** the inverse-RMSE `forecasting.forecast_tracker.ForecastTracker` (which weights ARIMA/Monte Carlo/Holt-Winters/CNN-LSTM by recent realized accuracy instead of fixed fractions, in `_blend_with_skill`'s skill branch) is wired behind `settings.FORECAST_SKILL_WEIGHTING_ENABLED` (default `False`, mirroring the `FORECAST_USE_GARCH_SIGMA` opt-in convention). When `True`, a persistent `ForecastTracker` (self-provisioning its `forecast_errors` table in `quant_platform.db`, no migration) is injected into every `ForecastingEngine` construction — `main_orchestrator.py` (both the `EngineContext.build` path and the `run_pipeline` fallback) and `engine/advisory.py`; when `False` (the default) `tracker=None` → byte-identical static blend. `FORECAST_SKILL_WINDOW_DAYS` default was raised `60 → 180` (it MUST exceed the 90-day max horizon: a 'completed' h=90 row needs `forecast_ts ≤ now-85d` while the window only counts `forecast_ts ≥ now-WINDOW`, so 60 left h=60/h=90 with mutually-exclusive eligibility bands and they could never warm up). Both are in `gui/env_io.py` `ALLOWED_KEYS`; new uplift backtest `tests/test_forecast_skill_uplift.py` (slow-marked, opt-in). **New env vars:** `FORECAST_USE_GARCH_SIGMA` (bool, default `True`), `FORECAST_PROPHET_WEIGHT` (float, default `0.25`), `FORECAST_SKILL_WEIGHTING_ENABLED` (bool, default `False`), `FORECAST_SKILL_WINDOW_DAYS` (int, default `180`). **Connection reuse (2026-07, PR A hot-path):** `ForecastTracker` previously opened a fresh `sqlite3.connect(...)` (+ WAL PRAGMA) on every call (~12/ticker/cycle); it now holds ONE cached connection (`self._conn` via `_get_conn()`, `check_same_thread=False`, WAL + `busy_timeout=5000`) guarded by `self._lock` (`threading.Lock`) so every method reuses the handle and it is safe under the orchestrator's parallelized advisory loop; `_ensure_table()` still uses a short-lived connection so the db_path-swap error tests keep passing. **CNN-LSTM + Prophet model persistence (2026-07, PR C, opt-in via `settings.FORECAST_MODEL_PERSISTENCE_ENABLED`, default `False`):** both models were previously retrained from scratch on EVERY `generate_forecast()` call per ticker per cycle — the CNN-LSTM's own docstring already flagged this as unable to scale, and it is by far the dominant per-cycle CPU cost. `forecasting/model_persistence.py` (new module) provides dependency-light `artifact_path(prefix, ticker, suffix)` / `is_fresh(path, retrain_days)` / `touch(path)` helpers — ONE fixed (non-dated) artifact per ticker under `ml_models/forecast_cache/` beneath `settings.LOCAL_DATA_ROOT` (default `~/.stockpy_local`, external to every git checkout/worktree — see `docs/architecture/data-layer.md`'s `settings.LOCAL_DATA_ROOT` subsection for the full layout) (mtime IS the staleness clock; simpler than the glob-latest dated-history convention `ml/lgbm_ranker.py`/`ml/meta_labeling.py` use, since only the most recent fit ever matters for a live forecaster). `run_prophet_forecast(..., ticker=None)`: when a fresh (`< FORECAST_MODEL_RETRAIN_DAYS`, default 7) `prophet_{TICKER}.pkl` exists, `model.fit()` is skipped entirely — only `.predict()` runs on the pickle-loaded model; otherwise fits fresh then pickles the fitted model. `run_cnn_lstm_forecast(..., ticker=None)`: same pattern but split across three artifacts — `cnn_lstm_{TICKER}.keras` (native Keras `model.save()`/`tf.keras.models.load_model()`, not pickled) plus `cnn_lstm_{TICKER}_scaler_x.pkl` / `_scaler_y.pkl` (the train-only-fit `MinMaxScaler`s, pickled) — a cache hit skips the 50-epoch `Sequential(...).fit()` entirely and just transforms the latest lookback window through the loaded scaler + model. **Scoped to the direct multi-step path only** (`days_forward is None`, the path `generate_forecast` actually uses) — the single-horizon `days_forward`-set path is intentionally left untouched (out of scope) rather than handling a horizon-count mismatch between a cached multi-step model and a single requested horizon; a defensive `cached_model.output_shape[-1] != len(horizons)` check exists anyway and falls through to a fresh fit on mismatch. `generate_forecast` threads `ticker=persist_ticker` (the already-existing `symbol` extraction, `None` when the row carries no real `Symbol`/`Ticker` so ad-hoc/test calls never touch the on-disk cache) into both calls. Behavior-preserving BETWEEN retrains (same fitted weights → same forecast for repeated calls within the retrain window) — only WHEN a fit happens changes; any load/inference failure (missing library, corrupt/unreadable artifact, insufficient rows, horizon mismatch) degrades to a fresh fit, never raises (CONSTRAINT #6). When the flag is `False` (the default) every call retrains from scratch exactly as before persistence existed — matches the `FORECAST_USE_GARCH_SIGMA`/`FORECAST_SKILL_WEIGHTING_ENABLED` opt-in convention. **New env vars:** `FORECAST_MODEL_PERSISTENCE_ENABLED` (bool, default `False`), `FORECAST_MODEL_RETRAIN_DAYS` (int, default `7`, mirrors `regime/hmm_regime.py`'s `HMMRegimeDetector(retrain_freq_days=7)` convention). Both are in `gui/env_io.py` `ALLOWED_KEYS` and the Settings Manager layout. **Forecast reliability curve (2026-07):** `ForecastTracker.get_forecast_reliability_curve(symbol=None, horizon_days=None, n_bins=10, min_per_bin=3) -> pd.DataFrame` bins the realized percent error `(actual_price - forecast_price) / actual_price` over completed `forecast_errors` rows (`actual_price IS NOT NULL`) into fixed `[-0.5, 0.5]` buckets per `(model_name, horizon_days)` group — a genuinely distinct concept from `evaluation_engine.py`'s `calibration_curve()` (conviction-vs-win-rate from closed trades, not forecast accuracy). Bins with fewer than `min_per_bin` rows get `mean_pct_error=NaN` (never fabricated — CONSTRAINT #4); empty/no-data returns the correct empty schema, never raises (CONSTRAINT #6). Surfaced as a new sub-section in the GUI Observability tab's Forecast Skill panel (`gui/panels/observability.py::_render_observability_forecast_skill`). **CNN-LSTM subprocess isolation (2026-07-23, issue #381, `docs/known_issues/cnn_lstm_tf_deadlock.md`):** `run_cnn_lstm_forecast`'s TF-touching work (model fit+predict, and cached-model load+predict) can now run in a persistent `multiprocessing` "spawn" worker pool instead of in-process, behind `settings.CNN_LSTM_SUBPROCESS_ISOLATION_ENABLED` (default `False`). This fixes the deadlock at PROCESS scope rather than module scope — TensorFlow and pyarrow each ship a colliding Abseil symbol, and whichever library's Python-level init runs first in the process wins it; a fresh `spawn` worker process makes that ordering fully controllable regardless of what the parent process (`main.py`/`main_orchestrator.py`/`pipeline/production_steps.py`, all of which import pandas before `forecasting_engine`) already imported. New repo-root modules `cnn_lstm_worker.py` (the fit/predict/load payload — imports tensorflow before anything else, and deliberately does NOT live inside `forecasting/` since that package's `__init__.py` eagerly imports pandas via `ForecastTracker`) and `cnn_lstm_process_pool.py` (the persistent pool manager: `spawn` context, warm initializer, `run_in_subprocess(func, args, timeout_seconds, max_workers)`). All pandas-dependent feature engineering/windowing/scaling stays in the parent process unchanged; only numpy arrays and JSON-safe primitives cross the process boundary. Any subprocess failure (timeout, broken pool, a real training exception) is caught by the existing outer `try/except` and degrades to the zero-result sentinel (CONSTRAINT #6) — never blocks the pipeline. **New env vars:** `CNN_LSTM_SUBPROCESS_ISOLATION_ENABLED` (bool, default `False`), `CNN_LSTM_PROCESS_POOL_WORKERS` (int, default `1`, recommended `3` for multi-core systems), `CNN_LSTM_SUBPROCESS_TIMEOUT_SECONDS` (int, default `300`). Defense-in-depth companion fix: `main.py`/`main_orchestrator.py`/`pipeline/production_steps.py` each gained a guarded `import tensorflow` before their own `pandas` import, restoring PR #387's intended entry-point-level protection for whoever leaves isolation off. **Not verified against the real native deadlock** — this round's dev/CI environment could not reproduce the original macOS arm64 + Framework-Python repro environment; see the known-issues doc's Round 5 section before relying on this in production.
- **strategy_engine.py** — signal generation with calibrated momentum/trend weights and ATR-based volatility corridors (buy zone / hold range / trim-stop). Uses an Aroon Oscillator chop-filter to suppress false-positive MACD signals. Position sizing (`_calculate_kelly_sizing`) is volatility-targeting + estimated-p fractional Kelly (see `sizing/`) — no longer a score-derived formula. **Dedicated sell-side range (`apply_sell_side_range`):** alongside the legacy single-corridor `apply_tactical_ranges` (`buyRange`), `evaluate_security()` now ALWAYS emits a first-class `sellRange` string for every Action Signal. Active long signals (STRONG BUY/BUY/HOLD) yield `"Sell Zone: $LO - $HI | Stop @ $STOP"` where LO=`price + 1.5*ATR`, HI=`max(price + 3*ATR, forecast_price)` (forecast wins only when >ATR ceiling — never fabricated when forecast_price=0), STOP=`chandelier_long` (fallback `price - 2.5*ATR`, clamped ≥ $0.01). RISK REDUCE / unknown signals fail closed to `"Sell Now @ market | Stop @ $STOP"` (chandelier_long, fallback `price - 1.0*ATR`). Lookahead-free: consumes only the already-causal ATR, Chandelier Exit, and `Forecast_30` already flowing into `evaluate_security`.

**Stage 1.7 — Per-Strategy Bootstrap-Conservative Kelly (current):**
- When `strategy_id` is provided, delegates to `sizing.kelly.kelly_sizing_for_strategy(transactions_store, strategy_id, realized_vol)` which:
  1. Calls `estimate_win_rate_and_payoff_per_strategy()` to filter closed trades to `strategy_id`.
  2. Cold start (< 30 per-strategy trades): falls back to `volatility_target_weight(realized_vol)`, tagged `"vol_target_fallback"`. ALWAYS explicitly logged.
  3. Warm path: runs `bootstrap_kelly_confidence(returns, n_bootstraps=1_000)` and returns the **5th-percentile** Kelly fraction — the "epistemic humility" sizing (conservative until the edge estimate is stable at > ~200 trades). Tagged `"bootstrap_kelly_5th_pct(n=...,k5=...,k50=...,k95=...)"`.
- When `strategy_id` is None (backward-compatible): uses the global-pool aggregate `estimate_win_rate_and_payoff()` point estimate. Tagged `"aggregate_kelly"` or `"vol_target_fallback"`.

- **risk/etf_transmission.py** — ETF volatility-transmission MEASUREMENT layer (Ben-David, Franzoni & Moussawi 2018, "Do ETFs Increase Volatility?", *Journal of Finance* 73(6)), wired by `pipeline/production_steps.py::_apply_etf_transmission` (called from `StrategyEvalStep.run` immediately after `_apply_sector_heat_factor`, NOT before `global_registry.run_pre_compute()` — nothing in pre_compute consumes these columns). Three `config.COLUMN_SCHEMA` columns (`ETF_Ownership_Pct` percent, `ETF_Comovement_R2` number, `ETF_Primary_Wrapper` string) — not a `SignalModule`, no `SIGNAL_WEIGHTS` entry, no scoring effect. Now consumed by two sizing-path features documented under `sizing/position_sizer.py` above: the per-name `transmission_multiplier` derate and the portfolio-level `build_transmission_adjusted_cov`. **The crux of the design is market-residualized, not naive, R²**: a naive R² of a stock on its sector-ETF composite is high for every large-cap regardless of ETF ownership (both legs load on the same market factor) — that would be a market-beta derate wearing an ETF costume. `compute_market_residual_r2(stock_bars, composite_returns, market_bars, window=60, min_obs=60)` therefore residualizes BOTH legs against `settings.ETF_HOLDINGS_MARKET_PROXY` (default `SPY`) first (`β = Cov(r, r_mkt)/Var(r_mkt)`, `u_t = r_t - β·r_mkt,t`) and correlates the two residual series, following `processing_engine.calculate_rolling_beta`'s exact alignment contract (contemporaneous `.rolling(window)`, `join="inner"`, never forward-filled — lookahead-free by construction, pinned by three perturbation tests in `tests/test_etf_transmission_lookahead.py`, one per leg since the market proxy drives both residualizations). `build_etf_return_composite(holdings_by_etf, etf_bars, market_proxy="SPY")` builds the ownership-weighted composite return series per constituent over NON-market wrappers only — the market proxy is EXCLUDED from the composite (used solely as the residualization leg), so a name whose only covered wrapper IS the market proxy has an identically-zero residual and reports `ETF_Comovement_R2 = NaN`, never a fabricated number (the identification limit surfacing as missing data, CONSTRAINT #4). `compute_etf_ownership(holdings_by_etf, shares_outstanding, exclude_symbols=...)` sums `shares_held` across covered baskets over `shares_out ≈ Market Cap / Price`, guarded on both being `> 0` (`FundamentalDataDTO.market_cap` defaults to a fabricated `0.0` — a naive divide would yield `inf` on exactly the names whose fundamentals failed); a basket reporting no `shares_held` makes the SUM unknowable (`NaN`), never silently smaller. `primary_wrapper(holdings_by_etf)` returns the largest-weight covered ETF per name — required for operator explainability (`sizing/position_sizer.py` names "why is this name derated?" as a design goal) — ranking by NAV `weight` when available, else `shares_held`. **Composition drift**: a name added to a wrapper last week has no tethered history, so the module chooses NaN-until-full-window-coverage (`< max(window, min_obs)` aligned observations → `NaN`) rather than an understated partial-window number. **Explicit exclusion set** (`ETF_TRANSMISSION_WRAPPERS ∪ {ETF_HOLDINGS_MARKET_PROXY} ∪ ETF_TRANSMISSION_EXCLUDED_SYMBOLS`): a ticker that is ITSELF an ETF is excluded from all three columns — its ownership/R² against its own basket is 1.0/1.0, a maximum derate for a trivially wrong reason. `risk/etf_transmission.py` performs ZERO I/O (pure math over holdings dicts / OHLCV DataFrames the caller supplies) and consumes Agent-owned `data/etf_holdings.py`'s `ETFHolding` dataclass duck-typed (`holding_symbol`/`weight`/`shares_held`/`as_of_date`), never importing it, so the two modules land independently. `_apply_etf_transmission` NaN-fills all three columns FIRST before any branch, lazy-imports `data.etf_holdings`/`risk.etf_transmission` inside the function body, fetches ETF bars through the existing `DataEngine.fetch_technical_raw_cached` path (never a second batched `yf.download` — `research_engine.fetch_returns_for_clustering` is deliberately the only one in the repo), and logs its per-cycle fallback tally ONCE at INFO with counts, never once per name. **Deliberately NOT implemented**: the paper's literal arbitrage-gap regression (stock return on lagged ETF-price-vs-NAV mispricing `Δ_t = p_t - ι_t`) — reconstructing the synthetic basket needs price history for the FULL constituent set (SPY = ~500 names) while `tech_raw` only carries the operator universe, and free daily NAV/IIV history is unavailable; a low-coverage basket proxy would be fabricated data, so this is a Phase-2 follow-up gated on a real NAV source, not on more code.
