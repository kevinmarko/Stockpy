- **Background job execution (`api/_jobs.py`, `api/control_api.py`'s `POST /jobs`/`GET /jobs/{id}`/`POST /jobs/{id}/cancel`/`GET /jobs/{id}/stream`, PR #487)** — a closed-enum background-process runner previously undocumented here: `JobType` dispatches to one hardcoded-argv `launch_*` function in `shared/orchestrator_runner.py` per type, gated by `settings.JOBS_API_ENABLED` (master switch) + the same fail-closed `ORCHESTRATOR_DAEMON_TOKEN` command token as `POST /run`. Backs the `Console.tsx` screen's one-click Preflight/Pytest/Advisory/Verify/Gravity-Audit/Backtest buttons (`createJob`/`getJobStatus`/`cancelJob` in `src/api/client.ts`, live output via `<LogStream>`'s SSE stream). Cancellation (`POST /jobs/{id}/cancel`) guards against completed jobs, reporting `cancelled: false` honestly without overwriting terminal exit status (`success`/`failed`), and `Console.tsx` renders `"—"` for non-running jobs. **`JobManager.cancel_job()` uses `shared/orchestrator_runner.py::stop_run_detailed()` (2026-08 fix), not the plain bool-returning `stop_run()`** — the underlying `stop_run()` conflates "the process was already dead when we looked" with "we just killed it" into the same bare `True` (documented in its own docstring's "or was never running" clause), and a `cancel_job()` built on a separate `is_running()` pre-check plus that bool left a real, if narrow, race: a process racing to ANY exit code (not just the `rc==0` case an earlier fix caught) between the check and the kill attempt could still get mislabeled `"cancelled"`. `stop_run_detailed()` returns a `StopOutcome(stopped, already_stopped)` from ONE atomic-as-possible liveness+kill attempt (no separate pre-check), so `cancel_job()` can tell "it finished on its own" (any exit code) apart from "an earlier call already cancelled it" and never flips `rec.cancelled` in either case — the double-cancel case correctly reports `cancelled: true` (it WAS cancelled, just not by this call) instead of a misleading "could not be confirmed". `stop_run()` itself is kept as a thin backward-compatible wrapper over `stop_run_detailed()` (its former callers were in the Streamlit desktop app, deleted 2026-09). - **Options-strategy realism: a third "paper-broker realistic" quick action, distinct from the naive/ungated bulk-options button (2026-08)** — prompted by an operator running the "🧪 Bulk Validate Options Strategies" button (`validation.harness --strategies` against `STANDARD_OPTIONS_STRATEGIES`) and getting confused by uniformly bad Sharpe/DSR/MaxDD numbers for real strategy names like "Iron Condor"/"Put Credit Spread".   **Gemini Live API WebSocket Streaming (`/ws/chat/live`, 2026-08)** — Bidirectional, low-latency voice and text streaming over WebSockets between the Pilots PWA frontend and Google Gemini (`gemini-3.1-flash-live-preview`), grounded in platform portfolio and strategy state.
  - Gated by `settings.AI_GENERATION_API_ENABLED` and `settings.GEMINI_LIVE_CHAT_ENABLED` with token authentication via `STATE_API_TOKEN` (`?token=` or `Authorization: Bearer` header, 4003 on unauthorized/disabled). Requires `settings.GEMINI_API_KEY`. **When `STATE_API_TOKEN` is unset, the connection is allowed ONLY from a loopback client** — `api/ws_api.py::_check_ws_token` checks the WebSocket's `.client.host` against `api.auth.is_loopback_host` (the same shared definition `api/auth.py::require_read_token` uses for HTTP endpoints), rather than the earlier, looser "no token configured → always open regardless of origin" rule. This matters because `scripts/Caddyfile` proxies `/ws/chat/*` to the Data API, so a non-loopback caller reaching this endpoint through that proxy with no token configured is refused (4003) exactly like a sibling HTTP endpoint would 503, instead of being let straight in.
  - Audio Format: 16 kHz 16-bit linear PCM mono input (mic capture downsampled in browser via Web Audio API) and 24 kHz 16-bit linear PCM mono output (streamed from Gemini and played via `AudioContext` with instant interruption flushing).
  - Grounding Tools: Connected with read-only tools (`list_all_pilots`, `get_pilot_holdings`, `get_pilot_recent_trades`, `get_current_portfolio`, `get_platform_status`) executed dynamically (`asyncio.to_thread`) with live responses sent via `session.send_tool_response`.
  - **Concurrency:** the endpoint runs two independent `asyncio` tasks per connection (`client_to_gemini` relaying browser→Gemini input, `gemini_to_client` relaying Gemini→browser output) that both write to the SAME WebSocket — every outbound frame is serialized through one `asyncio.Lock()`-backed `_send_json` helper rather than calling `websocket.send_json` directly from either task, since Starlette's `WebSocket` has no send-side locking of its own and two concurrent sends (e.g. a ping's "pong" reply racing the audio/transcript stream) could otherwise interleave partial writes on the wire.
  - **Transcript accumulation (frontend, `webapp/src/chat/useGeminiLive.ts` + `webapp/src/components/AIChatInterface.tsx`):** `input_transcription`/`output_transcription` events stream INCREMENTAL fragments of the utterance (mirroring how Gemini's own audio-transcription samples print each chunk with no separator), not the full cumulative text restated on every event — the frontend appends each fragment onto the still-open live message rather than replacing it, and `onTurnComplete` seals the trailing message (`ChatMessage.turnComplete`) so the next turn's fragments open a fresh bubble instead of continuing to append into the finished one.

### PWA Offline Support
The PWA supports offline mode using `vite-plugin-pwa` to cache standard assets and `workbox` for runtime caching.
A `NetworkFirst` runtime caching rule is configured for API `GET` requests (excluding SSE streams, handled by `webapp/vite.pwa-runtime-caching.ts`) to ensure data remains viewable when offline, falling back to cache only when the network request fails or times out.
