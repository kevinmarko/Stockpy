# Architecture: Simulation, Evaluation & Reporting Plumbing

> Part of the split-out `CLAUDE.md` System Architecture reference. See [../../CLAUDE.md](../../CLAUDE.md) for the index.

- **simulation_engine.py** — `vectorbt` parameter-sweep optimization plus `backtrader` event-driven backtests (0.1% commission / 0.05% slippage standard). Integrates survivorship bias warning prints using `universe_engine.py`. New strategies should be proven here before being wired into `strategy_engine.py`. **Degenerate-std guard (2026-07):** `cost_sensitivity_curve`'s std guard was hardened from an exact `== 0` check to `< 1e-12`, matching the repo-wide convention — see `CLAUDE.md`'s "Degenerate-std guard convention" bullet.
- **universe_engine.py** — S&P 500 point-in-time universe loader. Scrapes Wikipedia's current-constituents table to reconstruct the roster, loads local delistings from `data/delisted_tickers.csv`, and reports estimated survivorship bias. **Historical changes source (2026-08 fix)**: Wikipedia's "Selected changes" table (the additions/removals history) was removed from the live page entirely, which broke `fetch_and_cache_universe()` unconditionally on any fresh clone with no cache. Fixed two ways: (1) `settings.FMP_UNIVERSE_ENABLED` (default `False`) makes FMP's historical S&P 500 constituent-changes feed (`data/fmp_client.py::historical_sp500_changes`, dispatched via `data/fmp_universe.py::fetch_sp500_changes_via_fmp`) the PRIMARY source for the changes half, with the Wikipedia changes-table scrape demoted to a fallback — see `docs/FMP_INTEGRATION.md` §8 for the full writeup, including the honest "not verified against a live account" caveat. (2) Independent of the FMP feed, `fetch_and_cache_universe()`'s stale-cache fallback (previously only covering a network-request exception) now also covers a structural page-shape failure (too few tables, missing columns) — the same severity treatment, so a data-source shape change degrades to a cached snapshot rather than crashing every caller. `validation/harness.py::run()`'s call to `get_universe_with_survivorship_warning` is separately guarded (mirroring `simulation_engine.py`'s own pre-existing try/except around the same call) and degrades to an honest NaN/`None`-flagged `bias_report` sentinel instead of crashing the whole validation run.
- **research_engine.py** — realized slippage, CoVaR tail-dependency proxy, Brinson-Fachler attribution, portfolio heat.
- **evaluation_engine.py** — strategy performance evaluation. `evaluate_portfolio()`/`calculate_edge_ratio()` compute MAE (Maximum Adverse Excursion) and MFE (Maximum Favorable Excursion) from a real closed trade's genuine intra-trade OHLC path — `transactions_store.py`'s actual entry/exit timestamps sliced against real daily (optionally hourly, `settings.EXCURSION_INTRADAY_ENABLED`) bars, never a single bar or a fabricated stand-in; NaN (never 0.0) when no real trade + hold-period history is available (CONSTRAINT #4). **`calculate_equity_curve_metrics(equity_df, risk_free_rate=0.0) -> Dict[str, float]`** (module-level, alongside `calibration_curve`) computes Sharpe ratio, Calmar ratio, max drawdown, max-drawdown duration (days), and CAGR from an account equity curve (the exact shape returned by `data.historical_store.HistoricalStore.account_snapshot_history()` — `fetched_at`/`total_equity` columns). Vectorized (dedupes multiple same-day snapshots to the last one via `groupby`/`drop_duplicates`, no `.iterrows()`); every value is `NaN` — never a fabricated `0.0` — when there are fewer than `MIN_SNAPSHOTS_FOR_STATS` (20) distinct daily snapshots or `total_equity` has zero variance (Sharpe/Calmar undefined for a flat curve). Surfaced as four additional `st.metric` tiles in the GUI Analytics tab's Account Value Equity Curve section (`gui/panels/analytics.py::_render_account_equity_curve`). **Degenerate-std guard fix (2026-07):** the Sharpe guard (`returns.std(ddof=1) == 0`) and Calmar guard (`max_drawdown == 0.0`) were both exact-equality checks that let a near-zero-but-nonzero std/drawdown (floating-point noise from a flat/degenerate equity curve) explode the ratio instead of degrading to `NaN`; both are now `< 1e-12` / `abs(max_drawdown) < 1e-12`, matching `risk/etf_transmission.py::_DEGENERATE_STD` and the repo-wide convention documented in `CLAUDE.md`. Note this Calmar ratio is CAGR-based (`cagr / abs(max_drawdown)`, the textbook definition) and is NOT cross-comparable to `validation/harness.py`'s arithmetic-mean-annualized Calmar (`mean(returns) * freq / max_dd`) for the same underlying returns -- see that file's own bullet in `docs/architecture/validation-and-signals.md` ("Annualization-frequency wiring") for the sibling convention. **Brinson-Fachler `calculate_brinson_fachler` has two code paths sharing one name — an audit confirmed only one was correct (2026-08 fix):** the DataFrame-input branch (routed to `_calculate_brinson_fachler_compat`, used by `pilots/brinson.py`'s manual-input calculator) has always correctly decomposed active return into Allocation/Selection/Interaction effects, verified hand-computed to floating-point precision including the sum-to-active-return identity. The Series/array-input branch (called internally by `evaluate_portfolio()` — the real per-cycle orchestrator pipeline, via `pipeline/production_steps.py::StrategyEvalStep`) computed only Allocation and Selection, silently omitting Interaction entirely — this broke the fundamental Brinson-Fachler identity (`Allocation + Selection + Interaction == Active Return`) whenever both weight AND return differed between portfolio and benchmark for a sector (the general case), and the bad output landed directly in the live `BF_Allocation`/`BF_Selection` `config.COLUMN_SCHEMA` dashboard columns shown in every daily report. Fixed: the array-input branch now also computes `BF_Interaction = (w_p - w_b) * (R_p - R_b)` (identical formula to the compat path's `interaction_effect`), surfaced as a new `BF_Interaction` `config.COLUMN_SCHEMA` column (`"BF Interaction Effect"`, orchestrator-only like its siblings) and exported by `pipeline/production_steps.py`'s `StrategyEvalStep` alongside `BF_Allocation`/`BF_Selection`. `evaluate_portfolio()`'s two skip branches (zero total `position_size`; missing `sector`/benchmark data) default `BF_Interaction` to `0.0`, matching the existing convention for the other two columns. A new identity regression test (`tests/test_evaluation_engine.py::TestBrinsonFachler::test_series_path_interaction_effect_sums_to_active_return`) brings the array-input path's test coverage to parity with the DataFrame path's own pre-existing identity test. **A second, related fix in the same pass — duplicate-sector data loss in `pilots/brinson.py`:** `_calculate_brinson_fachler_compat`'s `pd.merge(..., on="sector", how="outer")` has no dedup check; two input rows sharing a sector name produced a Cartesian-product row set for that sector, silently collapsed by the downstream `{row["sector"]: {...}}` dict comprehension via key collision (aggregate totals stayed correct — that math is linear — only the per-sector `Sector Details` breakdown lost data). Rather than touch the shared engine (other callers depend on it, including the legacy/frozen `gui/report_viewer_helpers.py` calculator, which carries the identical latent bug and is out of scope), `pilots/brinson.py::compute_brinson_fachler` now hard-rejects (`ValueError` → HTTP 422 on `POST /portfolio/attribution/brinson-fachler`) any request whose rows contain a duplicate sector name, via a new `_find_duplicate_sectors` helper; `validate_brinson_fachler_rows` also surfaces the same condition as an informational warning for any other caller. `webapp/src/api/mock.ts::mockComputeBrinsonFachler` mirrors the same reject (mock/live parity — that mock reproduces the real math, not a canned fixture, per its own header comment).
- **transactions_store.py** — SQLAlchemy-backed transactions database for tracking active/closed trades. Backend is resolved through **db_config.py** (dual-backend config seam): defaults to a local SQLite file (`quant_platform.db`, WAL journaling); setting `DATABASE_URL` (e.g. a `postgresql://...` DSN, including a Supabase Postgres project) transparently switches every store onto Postgres with a pre-pinged pool (`DB_POOL_SIZE`=5, `DB_MAX_OVERFLOW`=10). `db_config.create_db_engine()` never logs the full URL (CONSTRAINT #3 — a Postgres DSN embeds `user:pass@host`; only the backend name is logged). **DB-outage resilience (2026-07):** `TransactionsStore()` construction does an eager connection (`Base.metadata.create_all`), so a remote-backend connectivity failure (DNS/network — e.g. an unreachable Supabase host) used to raise straight out of `engine.advisory._get_transactions_store()` and `StrategyEngine.transactions_store`, dead-lettering EVERY symbol's advisory evaluation for the cycle over what is, for the advisory pipeline, an optional position-sizing refinement. Both of those lazy-construction call sites now catch a construction failure, log ONCE, and substitute **`transactions_store._OfflineTransactionsStore`** — a read-only stub whose `closed_trades_df()`/`open_trades_df()`/`get_trade_history()` return empty DataFrames (the same "zero closed trades" cold-start shape `sizing/kelly.py` already falls back from to `volatility_target_weight` — CONSTRAINT #6) while `record_trade()`/`close_trade()` still raise (a trade that was never persisted must not be fabricated as recorded — CONSTRAINT #4). The stub is cached on the singleton/property so a DB outage doesn't retry-storm the failing host once per ticker in the universe. Covered by `tests/test_transactions_store.py` and Gravity `step_75_db_backend_resilience_audit` (renumbered from `step_74` by PR #209's Gravity split-brain consolidation, which resolved a same-day collision with `step_74_progress_indicator_audit`). **Operational note:** Supabase's direct-connect hostname (`db.<project>.supabase.co`) is IPv6-only in many regions/projects; on an IPv4-only network this manifests as `psycopg2.OperationalError: could not translate host name ... to address` even though the DSN/credentials are correct — use Supabase's Session/Transaction pooler hostname (`aws-0-<region>.pooler.supabase.com`, username `postgres.<project-ref>`) instead, which is IPv4-compatible and free.
- **`.agents/skills/` and `.claude/skills/`** — Agent-context Skills surface for this repo, auto-discovered by Antigravity and Claude Code respectively. Houses workflow skills including `stockpy-master-prompt` (master startup prompt, constraints, and audit ritual), `stockpy-quant-integrity` (distilled reference for CONSTRAINT #4/6, deployability gate, single source of truth), `strategy-validation`, `backtest-optimization`, `regime-model-tuning`, `alert-rule-authoring`, `bug-hunting`, `incident-triage`, `robinhood-execution`, `agentic-discovery`, `new-signal-module`, `new-pwa-screen`, `pilots-endpoint`, `mcp-widget-builder`, `jules-delegation`, and Supabase Postgres skills (`supabase`, `supabase-postgres-best-practices`). Coding agents working across the platform should load the relevant skill for guidance.
- **database_setup.py** — builds the SQLite schema (`DailySignals`, `ExecutionLogs`) dynamically from `config.COLUMN_SCHEMA`; never hardcode SQL column lists. `quant_platform.db` itself is **not** checked into git (gitignored via `*.db`, per-machine runtime state that accumulates local trades/signals/snapshots) — a fresh clone runs `python3 database_setup.py` once (creates `DailySignals`/`ExecutionLogs`), and `TransactionsStore`'s own `Base.metadata.create_all()` / `HistoricalStore`'s lazy table creation build the rest on first use. This was untracked from git on 2026-07-06 after a prior incident where `ml/registry.yaml` (a similar tracked, mutating file) was corrupted by a concurrent-PR merge — tracked files that mutate on every run are a recurring source of pull/merge data-loss risk.
- **diagnostics_and_visuals.py** — HTML report generation/rendering. `diagnostics_and_visuals.generate_html_report(portfolio_data, regime, output_path, *, yield_curve, credit_spread, sahm_rule, real_yield, audit_log=None, account_summary=None)` is the single HTML **rendering engine** (the legacy `reporting_engine.py`/`daily_report_template.html` pair was superseded and deleted 2026-07-09). It is no longer called inline by the orchestrators: `reporting/html_publisher.py` (`write_html_report`) is the extracted publishing layer that both `main.py` and `main_orchestrator.py` route through, and it in turn calls `generate_html_report` to render. **Report redesign (2026-06):** the embedded `HTML_REPORT_TEMPLATE` leads with **Holdings & P&L** (shares, avg cost, current price, market value, signed unrealized P&L $/%) and **Action & Rationale** (action signal w/ colour class + conviction meter, suggested position %, click-to-expand plain-English rationale). New optional keyword `account_summary: dict` renders a top **portfolio summary band** (total equity, buying power, total unrealized P&L, dividends received, position count, BUY/HOLD/SELL tally); when `None` (the `main_orchestrator.py` path) the band is hidden and rows degrade to "—" placeholders. Backward-compatible: field normalization accepts BOTH spaced pipeline keys (`"Action Signal"`, `"Robinhood Unrealized PL"`) and underscored advisory keys (`"Action_Signal"`, `"UnrealizedPL"`); market value / unrealized P&L are **derived** (`shares×price`, `(price−avgCost)×shares`) only when the Robinhood snapshot fields are absent (never fabricated for non-held symbols — those render "—"). Dependency-free client-side **search box + sortable columns** (vanilla JS, no DataTables/jQuery). `main.py._write_html_report()` sources holdings/P&L from the Robinhood `AccountSnapshot` positions (source of truth for account state, CONSTRAINT #4) and builds `account_summary` defensively (a degraded/empty snapshot omits the band, never aborts the report). Covered by `tests/test_html_report.py`.
- **reporting/html_publisher.py** — Report-publishing layer extracted out of `main.py` (`write_html_report(result, macro_dto)`, `write_state_snapshot`) so the Sheets + HTML publish logic is no longer inlined in the advisory entry point; both orchestrators call it instead. `write_html_report` renders via `diagnostics_and_visuals.generate_html_report` and also invokes `reporting.state_snapshot.write_state_snapshot` for the GUI-facing telemetry snapshot.
- **reporting/progress.py** — Cross-cutting, dead-letter-safe pipeline-progress reporter. `ProgressReporter(stages, *, run_id=None, output_dir=None)` is instantiated once per cycle by the orchestrator (`main_orchestrator.py`/`main.py`/`pipeline/*`) with the ordered list of stage names for that run; `start_stage(name, *, symbols_total=0)` advances to a new stage and resets the per-stage symbol counter; `advance_symbol(message="")` (thread-safe — safe to call from the parallelized per-ticker worker pools described under `main_orchestrator.py`/`engine/advisory.py` above) increments the completed-symbol count within the current stage; `set_message(msg)` updates a free-text status line without changing stage/counts; `finish(state="succeeded")` marks the run terminal (`"succeeded"` | `"failed"` | `"cancelled"`). Every call atomically writes `output/progress.json` (write-then-rename, mirroring `execution/kill_switch.py`'s `activate()` idiom) with the shape `{run_id, state, stage, stage_index, stage_total, symbols_done, symbols_total, percent, message, started_at, updated_at}`. Module-level `read_progress(output_dir=None) -> Optional[ProgressState]` is the read side — dead-letter resilient (CONSTRAINT #6): a missing, unreadable, or malformed `progress.json` degrades to `None`, never a fabricated/partial progress dict (CONSTRAINT #4). `clear_progress(output_dir=None)` removes the sentinel (e.g. at the start of a fresh run). Consumed by `desktop/daemon_runtime.py`'s `RunRecord` (gained a `progress` field mirroring the same shape, surfaced through `api/control_api.py`'s `GET /status` / `GET /run/{run_id}/status` and `gui/daemon_client.py`) and by `gui/orchestrator_runner.py::compute_run_progress(handle) -> Optional[RunProgress]` (`RunProgress` carries `percent`, `label`, `indeterminate` — `indeterminate=True` when a subprocess-backed run has no progress file yet, e.g. before the orchestrator's first `start_stage()` call). The Launcher tab (`gui/panels/launcher.py`) renders this as a live `st.progress` bar polling at `settings.PROGRESS_POLL_SECONDS` (default 5s, GUI-writable non-secret `ALLOWED_KEY`). **New GUI convention:** `gui/progress_ui.py::busy(label)` is a lightweight busy-indicator context manager (independent of `ProgressReporter` — for actions with no discrete stage/symbol structure, e.g. a single button click) applied across previously-silent GUI buttons so every long-running action gives immediate visual feedback.
