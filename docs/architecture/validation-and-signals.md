# Architecture: Validation & Pluggable Signals Package

> Part of the split-out `CLAUDE.md` System Architecture reference. See [../../CLAUDE.md](../../CLAUDE.md) for the index.

- **validation/purged_cv.py** — Combinatorial Purged Cross Validation (CPCV) logic with purging and embargo support. **Vectorized splitting engine (2026-08):** `CombinatorialPurgedCV.split()` is fully vectorized across NumPy boolean arrays, replacing per-row iteration and iloc lookups with precomputed per-block purge/embargo masks (`starts_within | overlaps_start | overlaps_end | embargo`). This yields a >7x acceleration across CPCV fold generation while producing bit-identical index splits to the reference algorithm. **MultiIndex support (2026-08):** `CombinatorialPurgedCV.split()` natively supports `pd.MultiIndex` frames (e.g. `(Date, Ticker)`) by extracting level 0 (the Date level) for all purge/embargo time comparisons instead of performing naive tuple lexicographic comparisons. A default `t1` (event end time) cannot be safely synthesized for a MultiIndex since a simple `shift(-1)` mixes rows across non-date levels unless contiguous-sort invariants are guaranteed; callers passing a MultiIndex MUST supply an explicit `t1` Series (indexed the same way as `X`), otherwise a `ValueError` is raised. Two further guards close the two ways that invariant can be violated silently: (1) the MultiIndex's level 0 must be sorted (`is_monotonic_increasing`) — the block-partitioning and purge/embargo logic both assume positional row order matches chronological order, which a MultiIndex built by e.g. `pd.concat`-ing per-ticker frames can easily violate without any other symptom; (2) an explicitly-passed `t1` must hold plain scalars comparable to the Date level, not MultiIndex tuples (e.g. from naively slicing `X.index` itself) — both raise a `ValueError` up front rather than failing later as a silent tuple-vs-timestamp comparison inside the purge loop. Verified against uneven per-date group sizes (e.g. a changing ticker universe where not every symbol has a row on every date) — purging is correct because it compares extracted dates, not block membership, so a block boundary landing mid-date does not leak. Tests: `tests/test_purged_cv_vectorization.py`, `tests/test_cpcv_paths.py`, `tests/test_harness_multiindex_t1.py`.
- **validation/metrics.py** — Deflated Sharpe Ratio (DSR), Probability of Backtest Overfitting (PBO), and CPCV path evaluation runner. `run_cpcv_evaluation()` gained an optional `cost_model_fn: Callable[[pd.Series, float], pd.Series]` parameter (2026-07 quant-integrity fix) — when supplied, every CPCV path's train/test returns are cost-adjusted via `cost_model_fn(returns, trial.get("turnover", 0.05))` BEFORE any Sharpe/PBO/DSR/drawdown statistic is computed, so PBO/DSR reflect the same net-of-cost basis the harness's other metrics already used instead of raw gross returns; `None` (the default) reproduces the prior gross-return behavior exactly. The return dict also gained four new genuinely-out-of-sample aggregates for the DSR-selected strategy — `mean_oos_max_dd`/`mean_oos_sortino`/`mean_oos_hit_rate`/`mean_oos_avg_trade_pct`/`mean_oos_turnover` — each the MEAN of that metric computed independently on every CPCV path's own held-out (purged+embargoed) returns, deliberately NOT a single concatenated equity curve (CPCV's combinatorial test-block reuse across paths would double/triple-count most dates in a naive concatenation; see the function's own docstring and `settings.VALIDATION_HARNESS_OOS_GATE_ENABLED` below). **Degenerate-std Sharpe/Sortino fabrication fix (2026-07):** `sharpe_ratio()` and this file's own inline per-CPCV-path Sortino calc guarded only against a bit-identical `std == 0`/`> 0`. A returns series that is mathematically constant but not bit-identical (e.g. an all-zero "no signal" book run through `StrategyValidationHarness._apply_cost_model`'s flat per-day cost deduction) produces a `std()` that's floating-point summation noise (~1e-16 to 1e-21), not exactly `0.0` — `mean/std` then exploded into an absurd, unbounded ratio instead of the honest `NaN` (CONSTRAINT #4; this is how the Pilots PWA's "Regime Navigator" marketplace card once showed a Sharpe of ~-7.7e16 when the `macro_regime_pit` backtest's macro/sector inputs were unavailable in a given environment, collapsing its book to a flat zero-return series). Both guards now require `std >= 1e-12` — the same degenerate-std threshold already used by `risk/etf_transmission.py`, comfortably above float noise and comfortably below any real strategy's daily-return std. Tests: `tests/test_metrics_sharpe_ratio.py`. **`probability_of_backtest_overfitting()` NaN-comparison guard (2026-08):** the in-sample-best trial's own OOS Sharpe (`oos_perf_of_best_is`) can be individually `NaN` on a path even when that path's in-sample row isn't all-NaN (e.g. a degenerate/constant test window for just that one trial) — `NaN < median` silently evaluates `False` in Python/numpy, so the path was previously counted as "measurable" but never as overfit, biasing PBO downward. The function now excludes such a path from `measurable_paths` entirely (mirroring the existing all-NaN-row `np.nanargmax`/`ValueError` skip immediately above it), consistent with CONSTRAINT #4: unmeasurable is excluded, never guessed in either direction. Tests: `tests/test_pbo.py`. **Annualization-frequency inference (`infer_annualization_freq`, 2026-08):** every function above accepted `freq: int = 252` but nothing in the `STRATEGY_REGISTRY` validation path ever overrode it, silently assuming daily observations for every strategy — `lgbm_ranker`'s own return series is a ~21-trading-day forward long-short spread (~20 observations/year, not 252), which inflated its reported Sharpe to an implausible ~24.9 via `sqrt(252/20)`-scale overstatement. `infer_annualization_freq(returns, default=252)` infers periods/year from a returns Series' own `DatetimeIndex` median consecutive-observation gap, snapping to `252.0` EXACTLY (bit-identical to the old hardcoded default) for any real daily trading calendar and falling back to the standard `365.25/median_gap_days` calendar-day formula for a genuinely coarser cadence; fails safe to `default` on <5 observations, a non-`DatetimeIndex` (e.g. `sector_quality_rank`'s MultiIndex panel — verified correct today since its own scored returns are daily, a documented scope boundary not a general MultiIndex mechanism), or any exception. Never raises. No existing function signature/default in this file changed — see `validation/harness.py`'s entry below for where it's actually wired in. Full write-up, the 29-strategy cadence survey, and `lgbm_ranker`'s real post-fix numbers: `docs/VALIDATION_STRATEGY_FIX_LOG.md`'s 2026-08-21 annualization-frequency entry.
- **validation/harness.py** — Master Strategy Validation Harness. Evaluates walk-forward stability, CPCV path metrics, and generates Jinja2 HTML validation reports. `StrategyValidationHarness.__init__` accepts `is_options_selling: bool = False` and `stress_returns_fn: Optional[Callable[[str,str], pd.Series]] = None`; when options-selling, `run()` replays the strategy across the tail scenarios (`validation/stress_scenarios.py`), attaches them to the report, prints the stress summary at the top, and renders a stress section in the HTML. `ValidationReport` carries `is_options_selling` + `stress_test_results` and exposes `stress_gate_passed`; its `deployable` property ANDs the existing PBO/DSR/Sharpe/MaxDD gates with the stress gate (the latter only applies to options-selling strategies and fails closed when stress results are missing). Exposes `StrategyValidationHarness.run_options_validation` delegating to `validation/options_harness.py`. **Genuine-OOS gate fix (`settings.VALIDATION_HARNESS_OOS_GATE_ENABLED`, default `False`, 2026-07):** `report.sharpe`/`.max_dd`/`.sortino`/`.calmar`/`.hit_rate`/`.avg_trade_pct`/`.turnover` were computed from `self.strategy_fn(X, y, X, y)` — a "test" set identical to the training set, an in-sample number feeding the `Sharpe > 0.5` / `MaxDD < 30%` deployability criteria while only PBO/DSR were genuinely out-of-sample. When the flag is `True`, `run()` passes its own cost model into `run_cpcv_evaluation` (see above) and replaces those seven numbers with the new `mean_oos_*` aggregates instead of the full-sample in-sample fit; `equity_curve`/`benchmark_curve`/`macro_benchmark_curve` are unchanged either way (still the full-sample series — a single non-overlapping OOS equity curve needs the AFML CPCV backtest-path-recombination algorithm, not implemented here). Default `False` reproduces every currently-recorded `docs/VALIDATION_STRATEGY_FIX_LOG.md` PBO/DSR/Sharpe/MaxDD baseline exactly — this sandboxed dev/CI environment has no live-market network access to re-verify the registered `STRATEGY_REGISTRY` fleet against the corrected numbers; see that log's 2026-07-29 harness-level addendum before enabling in production. Tests: `tests/test_metrics_cpcv_oos_aggregates.py`, `tests/test_harness_oos_gate.py`. This file's own full-sample Sortino calc got the same degenerate-std fix as `validation/metrics.py::sharpe_ratio()` above (see that bullet) — `downside_std >= 1e-12` instead of `> 0`. **Durable DB persistence (2026-08):** `run()`'s existing step 6c (`_append_validation_history`, appending to the worktree-local `reports/history/*.jsonl`) is now followed by a new step 6d, `_record_validation_run_to_db(report)` — a best-effort, dead-letter-resilient (CONSTRAINT #6) call into `validation/validation_history_store.py::ValidationHistoryStore.record_run()`, giving every run a second, durable home in the shared `validation_runs` DB table (see that module's own bullet below). `run_options_validation()`'s standalone entry point (which also calls `_write_json_summary`/`_append_validation_history` directly, outside `run()`) calls it too. A DB failure can never abort an otherwise-successful validation run, matching `_append_validation_history`'s own contract. Tests: `tests/test_validation_history.py::TestRecordValidationRunToDb`/`TestRunRecordsValidationRunToDb`. **Annualization-frequency wiring (2026-08):** `run()` computes `inferred_freq = infer_annualization_freq(y)` (see `validation/metrics.py`'s entry above) ONCE per call, immediately after `n_samples = len(X)`, and threads that single value explicitly into every Sharpe/Sortino/Calmar/DSR computation the function makes — both walk-forward Sharpes, the `run_cpcv_evaluation(freq=inferred_freq)` call (which alone propagates it through every CPCV path's internal Sharpe/DSR/Sortino), the gate-critical full-sample Sharpe, and both full-sample/OOS-gate Sortino and Calmar calculations (previously two independent hardcoded-`252` sites in this file, not even routed through `sharpe_ratio`). Deriving from `y` once (rather than re-inferring per Series) guarantees one run never mixes two different annualization assumptions across its own metrics — the failure mode that would otherwise let CPCV path Sharpes and the full-sample gate Sharpe silently disagree on cadence. Bit-identical for every daily-cadence `STRATEGY_REGISTRY` entry (proof: `tests/test_annualization_frequency.py`, plus a live controlled A/B spot-check — see the fix-log entry). Tests: `tests/test_annualization_frequency.py`. **Bulk CLI mode (2026-08, mirroring `scripts/refresh_validations.py`'s `--strategies`):** `main()`'s `--strategy` is now one half of a `required=True` mutually exclusive group with a new plural `--strategies` (comma-separated) — single-strategy invocations are byte-identical to before. Bulk mode is deliberately **options-strategies-only**: unlike `refresh_validations.py`, whose `STRATEGY_REGISTRY` gives every registered name a real adapter, `validation.harness`'s single-strategy branch only ever produces a real, name-specific result for a name in `validation.options_harness.STANDARD_OPTIONS_STRATEGIES` — anything else silently falls back to the fixed Buy-and-Hold-SPY placeholder regardless of the name passed. Bulk-validating a mix of placeholder names would therefore just re-run that identical placeholder N times under N different labels, which is worse than useless (it looks like N real results); `--strategies` instead hard-rejects any name outside `STANDARD_OPTIONS_STRATEGIES` with `SystemExit(2)` before running anything (fail closed — CONSTRAINT #6), pointing the operator at `scripts.refresh_validations --strategies` for equity/cross-sectional names. New `--workers`/`-w` (int, default 1, same flag name/semantics as `refresh_validations.py`) drives an optional `concurrent.futures.ThreadPoolExecutor`; new `--json` prints one final machine-readable line (`{strategy_name: {deployable, pbo, dsr, sharpe, max_drawdown[, error]}}`), matching `refresh_validations.py --json`'s exact convention. A per-strategy exception is caught and recorded rather than aborting the batch (`_run_options_bulk`); exit code is `0` iff every requested strategy is deployable, else `1` — the pre-existing single-strategy branch's own (unset) exit behavior is untouched. **Known, disclosed gap (not fixed by this change):** the webapp Commands screen's free-text Command Bar autocomplete (`webapp/src/commandParse.ts::valueSuggestions`) still sources ANY option whose name merely contains the substring `"strategy"` from the equity `strategyRegistry`/`REGISTERED_STRATEGIES` — so typing `validation.harness --strategies ` in the free-text bar still suggests equity names, not options-strategy names. Only the Form-Mode multi-select (`CommandFormBuilder.tsx`, via the new `optionsStrategyRegistry` prop) got the correct options-only source; fixing the free-text path needs threading a second registry through `parseCommandLine` and was judged out of scope here. **Pre-existing constructor bug fixed in the same change (confirmed present on `main` beforehand via `git stash` — unrelated to the bulk-mode addition itself, but blocking):** `run_options_validation()`'s throwaway `harness_inst = cls(strategy_fn=..., reports_dir=...)` omitted the two other required-positional constructor args (`universe_fn`, `cost_model`), raising `TypeError` on every single invocation — meaning the ONLY code path that ever gives a real per-strategy options result had never actually completed via the CLI (single- or bulk-strategy alike). Fixed by passing harmless placeholders for both (`universe_fn`/`cost_model` are never read by the three persistence methods called on that instance — only `self.reports_dir` and the `report` object are). Tests: `tests/test_harness_bulk_cli.py` (bulk CLI plumbing, rejection path, one-failure-doesn't-abort-batch, JSON shape, and a `TestRunOptionsValidationConstructorRegression` class exercising the real — non-monkeypatched — function end to end against synthetic price data to lock in the constructor fix). New manifest field: `options_strategy_registry` (see `scripts/build_command_manifest.py` and `docs/architecture/webapp-and-gui.md` below).
- **validation/validation_history_store.py** — `ValidationHistoryStore`: SQLAlchemy-backed durable log of every `StrategyValidationHarness.run()` call, matching `desktop/run_history_store.py`/`sizing/cap_audit_store.py`/`data/sector_correlation_store.py`'s established convention (own `Base`, own table resolved through `db_config.py`, a `readonly=True` database-level engine for read-only consumers). Exists because `reports/history/*.jsonl` and `reports/*_validation_summary.json` are worktree-local — this repo runs many simultaneous git worktrees, and an untracked file written in one is invisible from every other one (the same class of gap `settings.LOCAL_DATA_ROOT` was introduced to close for models/caches/logs) — so a validation run in one worktree was invisible to `pilots/validation_trend.py`/the Pilots PWA's Validation Trend chart running against a different worktree's API process. The `validation_runs` table is **append-only** (an autoincrement `id` PK, one new row per run) rather than upserted-by-key like `desktop/run_history_store.py`'s `pipeline_runs`, matching the JSONL history's own semantics — a strategy validated 40 times has 40 rows. Promotes `strategy_id`/`recorded_at`/`deployable`/`pbo`/`dsr`/`sharpe`/`max_drawdown`/`n_trials`/etc. to their own indexed columns for filtered queries, plus a `summary_json` TEXT blob holding the full `ValidationReport.to_summary_dict()` payload (equity/benchmark/macro curves, `family_multiple_testing` detail) — same shape as `PipelineRun.progress_json`. `pilots/validation_trend.py`'s `cross_strategy_snapshot()`/`validation_history_trend()` read this table FIRST (via a lazy, function-local import — confirmed dependency-light by `tests/test_pilots_strategy_matrix.py`'s AST guard, deliberately NOT `validation.harness`, whose top-level imports are far heavier; `validation` has no `__init__.py` so importing this one submodule doesn't transitively pull the package's other submodules) and fall back to the worktree-local file read only for a strategy the DB has no row for yet (e.g. one validated before this feature shipped). The `GET /strategy/validation-trend` response contract is unchanged — this is a backend source swap, not a new field, so `api/pilots_api.py`'s handler and `webapp/src/components/ValidationTrend.tsx` needed no changes. Tests: `tests/test_validation_history_store.py`, `tests/test_pilots_validation_trend.py`'s `*DbSource` test classes. **Test isolation:** every test in this suite that calls `StrategyValidationHarness.run()` for real (~25 files) would otherwise write a fake `strategy_id` row into the real, shared `~/.stockpy_local/quant_platform.db` on every test run — closed by a session-wide autouse fixture in the root `conftest.py` (`_isolate_validation_runs_db_in_tests`, mirroring the existing `_no_gdelt_throttle_in_tests`/`_no_fmp_throttle_in_tests` pattern) pointing the default DB resolver at an in-memory db unless a test passes its own explicit `db_url`.
- **validation/options_harness.py** — `OptionsValidationHarness`: institutional-grade options strategy simulator and backtest harness. Simulates multi-leg option strategies (Put Credit Spread, Call Credit Spread, Iron Condor, Bull Call Spread, Bear Put Spread, Long Straddle) with daily Black-Scholes mark-to-market pricing, profit-target exits, stop-loss triggers, expiration settlements, and execution cost deduction (`TieredCostModel`). Computes Sharpe, Sortino, Max Drawdown, Win Rate, Profit Factor, DSR, PBO, downsampled base-100 equity curves, and runs tail-scenario stress tests (`validation/stress_scenarios.py`). CLI executable: `python -m validation.options_harness --strategy "Put Credit Spread" --ticker SPY`.
- **scripts/refresh_validations.py** — regenerates `ml/registry.yaml`'s `STRATEGY_REGISTRY` deployability numbers (PBO/DSR/Sharpe/MaxDD) via `validation/harness.py` adapters per strategy; see `docs/VALIDATION_STRATEGY_FIX_LOG.md` for the dated per-strategy fix history. **Parallel validation & fast return slicing (2026-08):** `run_validations()` supports concurrent multi-strategy execution via `max_workers` (`--workers N` / `-w N` CLI flag) backed by a `concurrent.futures.ThreadPoolExecutor`, defaulting to sequential (`max_workers=1`). `_make_strategy_fn` optimizes return series extraction by bypassing expensive DatetimeIndex intersection when series indices align. **Degenerate-std guard (2026-07):** both of its Sortino-adapter guards (`_build_sortino_drawdown_adapter`, `_build_signal_replay_adapter`) had their `downside_std > 0` check hardened to `>= 1e-12`, matching the repo-wide convention documented in `CLAUDE.md`. **`--workers` + `lgbm_ranker` CPU-oversubscription follow-up (profiled 2026-08-14, PR #740 code-review finding — no code change landed):** the parallel-validation PR above left an open risk unaddressed — `lgbm_ranker` (`_build_lgbm_ranker_adapter`) is the one `STRATEGY_REGISTRY` adapter that genuinely retrains a real LightGBM model per CPCV fold (~45 real `.fit()` calls at CLI defaults), and LightGBM's `n_jobs`/`num_threads` is left at its library default (auto = all physical cores), so `--workers N > 1` naively looked like it could oversubscribe the machine relative to `--workers 1`. Measured, not assumed, before deciding whether to fix it: a synthetic-panel micro-benchmark (30 tickers × 300 dates, matching the real adapter's shape) ran `LGBMCrossSectionalRanker.train()` at increasing concurrency on a 10-physical-core machine — 3 concurrent calls finished in 1.46x a single call's time (vs. a 3x sequential ceiling); pushed all the way to 10 concurrent calls (far more than this codebase can ever actually create, since only one registry adapter is CPU-bound), wall-clock was still ~2.3x a single call, never worse than running sequentially. A real end-to-end CLI run (`lgbm_ranker` + 2 cheap adapters, `--n-cpcv-splits 5`) showed `--workers 1` vs. `--workers 3` wall-clock within measurement noise of each other (59.2s vs. 60.3s). **Conclusion: no code fix warranted** — capping LightGBM's thread count or excluding `lgbm_ranker` from the pool would trade away real, measured concurrency benefit to guard against a regression that does not reproduce on this hardware; the caveat and full methodology are documented in `run_validations()`'s own docstring instead, since the "only one CPU-bound adapter" precondition this conclusion depends on could change. `tests/test_refresh_validations.py::TestRunValidations::test_only_one_cpu_bound_adapter_in_registry` guards that precondition — it fails (forcing a re-profile) the moment a second adapter reuses `_build_lgbm_ranker_adapter`. Tests: `tests/test_refresh_validations.py`.
- **validation/stress_scenarios.py** — Tail-scenario stress testing for negatively-skewed options-selling strategies (whose rare-but-violent losses the full-sample MaxDD gate cannot catch). `STRESS_SCENARIOS` registers four dated shock windows — `OCT_2008` (Lehman, VIX>80), `FEB_2018` (Volmageddon/XIV blowup), `MAR_2020` (COVID crash+rebound), `AUG_2024` (yen carry unwind) — each a `StressScenario(start, end, expected_max_dd_for_short_vol, description)`; `.as_tuple()` yields the `(start, end, expected_max_dd_for_short_vol_strategies)` form. A caller supplies `returns_fn(start, end) -> pd.Series` (daily strategy returns for the window); `run_stress_tests()` produces `{name: StressResult}`. `compute_max_drawdown()` returns NaN (never fabricated 0.0) on empty data; `account_survived()` flags a blow-up if any daily return ≤ -100% or compounded equity hits 0. `passes_stress_gate(results)` = True iff every canonical window is present AND each `StressResult.passed` (survived AND `max_drawdown < MAX_STRESS_DRAWDOWN`=0.50) — fails closed on missing/errored windows. `format_stress_summary()` renders the top-of-report block.
- **validation/synthetic_diffusion_engine.py** — Phase 24 of `.claude/giant_master_plan.md`. A genuine score-based generative diffusion model: real Ornstein-Uhlenbeck forward marginal (`p(x_τ|x_0)`), a hand-rolled MLP score network trained with a full bias-corrected Adam optimizer, and a real reverse-SDE Euler-Maruyama sampler (`generate_synthetic_crash_paths`) producing VaR/CVaR via genuine tail-mean-beyond-quantile math (`compute_diffusion_var`). **Two confirmed gaps (2026-08-17 audit, `.claude/giant_master_plan_audit.md`):** (1) `tests/test_synthetic_diffusion_engine.py` has zero lookahead/perturbation coverage, and its VaR/CVaR test only asserts sanity bounds (`var > 0`, `cvar >= var`) despite the test file's own comments working out the exact expected numeric value — never asserted with `pytest.approx`; (2) the live `api/pilots_api.py` endpoint trains the model on `np.random.randn(10, ...)` i.i.d. Gaussian synthetic "historical data" rather than real historical returns for the requested symbol, defeating the stated purpose of learning empirical stylized facts (vol clustering, leverage effect, fat tails) from real data. Distinct from, and complementary to, `validation/stress_scenarios.py`'s four fixed dated shock windows above — this module was meant to generate a much larger synthetic scenario set, not replace the dated ones.
- **Options-selling deployability-gate coverage gap (2026-08-17 audit finding, not yet fixed)**: `validation/options_selling_backtest.py`'s harness (below) IS genuinely invoked by `scripts/refresh_validations.py`, but only by 6 generic SPY-only archetype proxies (`vrp_premium_selling`, `put_credit_spread`, `call_credit_spread`, `call_debit_spread`, `put_debit_spread`, `covered_call`) — **never by the actual named options-selling pilot modules the platform lets an operator execute**: `pilots/earnings_crush.py`, `pilots/vol_mispricing.py`, `pilots/dispersion_trading.py`, `pilots/zero_dte_engine.py`, `pilots/gamma_scalper.py` are all wired to real `POST .../execute` endpoints in `api/pilots_api.py` submitting trades into `PaperAccountStore`, yet none appear in `STRATEGY_REGISTRY`, none have a `docs/VALIDATION_STRATEGY_FIX_LOG.md` entry, and none get `validation/stress_scenarios.py`'s tail-shock coverage. `pilots/copula_stat_arb.py` (Phase 21) is likewise unregistered. `signals/options_flow_sentiment.py` below is the one fully-compliant options-desk signal — registered, gated, and honestly failed (DSR 0.906 < 0.95, documented in both the fix log and its own `docs/signals/` page) — worth using as the template when closing this gap. Full evidence: `.claude/giant_master_plan_audit.md`.
- **validation/options_selling_backtest.py** — synthetic per-day mark-to-market options-selling backtest (`simulate_options_strategy_returns` + 6 named `simulate_*_returns` wrappers: `put_credit_spread`/`call_credit_spread`/`iron_condor`/`call_debit_spread`/`put_debit_spread`/`covered_call`) backing both the `vrp_premium_selling` Pilot and `scripts/refresh_validations.py`'s 6 options-selling `STRATEGY_REGISTRY` adapters; see the module's own docstring for the full honesty contract (real-price-driven True_IVR/VRP proxies, real macro VIX/CREDIT-EVENT gating, constant entry-sigma per cycle, gross pre-cost returns). **Two internal, behavior-preserving refactors (2026-08, verified via a byte-for-byte regression test — `tests/test_options_selling_backtest_stress.py::TestSharedMtmHelperByteIdentical`):** (1) **shared per-day MTM/stop-loss helper** (`_simulate_leg_mtm_pnl`, `_OptionLeg`) — the 6 strategy branches used to each repeat their own ~25-40 line Black-Scholes mark-to-market + stop-loss loop; all 6 daily P&L formulas reduce algebraically to one expression (`cost_to_close = sum(short-leg prices) - sum(long-leg prices)`; `pnl = stock_pnl + (net_premium_raw - cost_to_close) * 100`), so each branch now only computes its own leg-count/premium guard and its own `max_risk`/stop-loss-threshold formula before delegating to the shared loop. (2) **process-local cycle-plan cache** (`_get_cycle_plan`/`_compute_cycle_plan`/`_CYCLE_PLAN_CACHE`) — the expensive, strategy-INDEPENDENT part of the simulation (the GJR-GARCH fit, IVR/VRP proxies, real macro DTO reconstruction, and the one `generate_strategy_pricing_matrix()` call made per ~21-trading-day cycle) is memoized on `(ticker, start, end, sha256(closes content))` — content-based, not identity-based, so it can never silently reuse a stale plan for two calls sharing a nominal window but different underlying price data — eliminating the up-to-6x redundant recompute a full `refresh_validations.py` registry sweep previously paid (all 6 adapters independently walk the same `(ticker, start, end)` window). Cache is process-local, never evicted mid-run (matches the CLI's short-lived-process lifetime); `_reset_cycle_plan_cache()` is a test-only utility. No public function signature changed. Tests: `tests/test_options_selling_backtest_stress.py` (`TestSharedMtmHelperByteIdentical`, `TestSharedMtmHelperDirectFormulaEquivalence`, `TestCyclePlanCacheAvoidsRedundantRecompute`).

  - **signals/timeseries_momentum.py** — Moskowitz/Ooi/Pedersen time-series momentum SignalModule.
  - **signals/cross_sectional_momentum.py** — Jegadeesh-Titman (1993) cross-sectional momentum SignalModule. Uses the two-phase `pre_compute` / `compute` hook pattern: `pre_compute` runs once to rank the full universe; `compute` reads the rank from `context.xsec_percentile_ranks`. Score = `2 * (rank - 0.5)` ∈ [-1, +1]. Default weight = 15.0.
  - **signals/rsi2_mean_reversion.py** — Connors-style RSI(2) long-only mean-reversion SignalModule. Unlike every other module, its score is in `[0.0, 1.0]` (long-only, no short analogue), not `[-1.0, 1.0]`. Trend filter: `Close > SMA_200`. Entry: `RSI_2 < 10`, scaled linearly to 1.0 as RSI(2)→0. Already-reverted guard: `Close > SMA_5` forces score to 0 (the bounce already happened). Overrides `is_active_in_regime()` to return `False` (fully suppressed, not just down-weighted) when `market_regime` is `RECESSION`/`CREDIT EVENT` or `vix > 30` — mean reversion is regime-fragile. Default weight in `settings.SIGNAL_WEIGHTS` is `10.0`, matching the established weight scale of the other modules (10–45). See `tests/test_validation_rsi2.py` docstring for an empirical backtest finding: the long-only trend filter alone already fully excludes 2008 exposure for this strategy, before the regime gate even applies — the gate's mitigating effect is load-bearing only for 2020 in that backtest.
  - **signals/multifactor.py** — Fama-French-style multifactor SignalModule (Value, Quality, Low-Vol, Size — Hou-Xue-Zhang (2020) priors; momentum is the separate `cross_sectional_momentum` module). Two-phase hook pattern: `pre_compute(universe_df, context)` reads raw factor inputs (`book_to_market`, `earnings_yield`, `quality_factor_score`, `low_vol_score`, `log_market_cap`, `Market Cap` — written into `dashboard_df` by `processing_engine.calculate_fundamental_metrics()`), excludes tickers with `Market Cap < settings.MULTIFACTOR_MICROCAP_THRESHOLD` (default $300M) from the cross-sectional z-scoring population entirely, z-scores each input and winsorizes at ±3 (`_zscore_winsorize()`), averages `book_to_market_z`/`earnings_yield_z` into `Value_Z`, negates the size z-score into `Size_Z` (smaller = positive), and averages all four into a `Multifactor_Composite` (re-clipped to ±3). Stores per-ticker results in `context.multifactor_scores`. `compute(row, context)` maps `Multifactor_Composite` to `[-1, +1]` via `tanh(z / 2)`; microcap-excluded or data-unavailable tickers get a neutral `0.0` score (never fabricated exposure). Default weight in `settings.SIGNAL_WEIGHTS` is `15.0` — note this deviates from the `0.15` originally specified for this task; it was rescaled to match this codebase's existing points-scale weight convention, where `contribution = score[-1,1] * weight` and other modules' weights range 10–45 (0.15 would be numerically inert at that scale). **Degenerate-std guard (2026-07):** `_zscore_winsorize()`'s `std == 0.0` guard was hardened to `std < 1e-12`, matching the repo-wide convention documented in `CLAUDE.md` (this feeds the live `Multifactor_Composite` column).
  - **signals/regime_multiplier.py** — `RegimeMultiplierSignal` deliberately carries NO directional alpha: `compute()` always returns `score=0.0` regardless of input, so it contributes nothing to `SignalAggregator`'s weighted-sum `final_score` even with a nonzero weight (its `settings.SIGNAL_WEIGHTS["regime_multiplier"] is explicitly `0.0`, structurally enforcing this, not just by convention). It carries `context.macro.hmm_risk_on_probability` (the `regime/hmm_regime.py` second opinion) through its `confidence` field instead — defaulting to `1.0` (neutral) when the HMM didn't run. `StrategyEngine.evaluate_security()` reads `outputs['regime_multiplier'].confidence` from `aggregator.aggregate()`'s returned `outputs` dict (already exposed for introspection) and multiplies the final Kelly Target by it, then re-clamps to `settings.MAX_POSITION_WEIGHT` — this is a position-sizing scalar, not a score input, and is the only signal module wired this way.
  - **volatility/iv_engine.py** — extracts ATM option implied volatilities, handles calendar-30-day linear interpolation, lookahead-free true IVR, and Volatility Risk Premium (VRP) calculation.
  - **volatility/bootstrap_iv_history.py** — CLI script to backfill historical ATM IVs in `iv_history`.
  - **pairs/cointegration.py** — implements Engle-Granger ADF cointegration, AR(1) mean reversion half-life estimation, and rolling ADF p-value checks.
  - **pairs/kalman_hedge.py** — dynamic hedge ratio tracker/filter (batch Kalman Filter and step-by-step Kalman tracking) using `pykalman`.
  - **pairs/simulation.py** — event-driven Backtrader backtest runner for pairs.
  - **signals/pairs_trading.py** — pairs trading signal generator.
  - **signals/options_flow_sentiment.py** — `OptionsFlowSentimentSignal(SignalModule)`: evaluates net directional options order flow sentiment from live dashboard columns, `SignalContext`, or persisted UOA records. Normalized score in `[-1.0, +1.0]` with dynamic confidence (0.85 on active directional flow, 0.5 on neutral, 0.0 on missing data). Default weight in `settings.SIGNAL_WEIGHTS` is `10.0`.
